# 设计决策流程（需求 → 页面结构）

> 本文件是 BeP skill 的**设计决策层总纲**：规定在生成任何页面之前必须完成的判断。
> 执行层（组件、模板、校验）解决「怎么画对」，本文件解决「该画什么」。

---

## 适用与边界

- **适用**：任何页面生成请求。页面类型明确且字段已给出时，本流程可快速通过（见「执行强度」两档）。
- **不适用**：纯组件样例页、纯规范问答、纯代码修复——这些直接走执行层。
- **不替代**：`page-type-rules.md`（页面类型）、`information-architecture.md`（IA）、`interaction-design.md`（交互）、`page-templates.md`（组件落地）、组件文档。

### 裁决顺序

设计决策层插在铁律之后、组件文档之前：

```
SKILL.md 设计决策铁律(P0–P3) > SKILL.md 执行铁律(P4–P5) > design-process.md
  > information-architecture.md > page-type-rules.md > interaction-design.md
  > pc-ux-principles.md > components-*.md > bep-components.js > validate-page.js > RAG
```

冲突时以更靠前者为准，并在交付说明中写明牺牲了什么。**不允许用执行层理由推翻设计层结论**（例：不能因为「组件库里只有这个」就改变页面类型判断）。

## 一、十步决策链

| # | 步骤 | 产出 | 前置读取 | 不通过时 |
|---|---|---|---|---|
| 1 | 理解需求 | 业务目标 + 用户任务清单 | 本文件 §二 八问 | 关键项无答案 → 走「待确认 + 假设推进」 |
| 2 | 判断角色 | 角色 × 任务 × 权限矩阵 | 本文件 §三 | 多角色且差异大 → 必须在卡里列出，不允许只做单角色 |
| 3 | 建立信息架构 | 模块树 + 页面清单 | `information-architecture.md` | 模块边界不清 → 先定业务对象再定模块 |
| 4 | 建立任务流 | 主路径 + 分支 + 来路/去路 | 本文件 §四 | 任务流断点 → 回退到步骤 3 补页面 |
| 5 | 确定页面类型 | 每页一个类型判定 | `page-type-rules.md` | 一页多类型 → 拆分或明确主类型 |
| 6 | 设计页面结构 | 模块顺序 + 信息优先级 | `page-type-rules.md` 骨架 | 结构顺序与任务流不一致 → 以任务流为准 |
| 7 | 设计交互 | 跳转/弹层/反馈/状态/异常 | `interaction-design.md` | 缺状态 → 补齐后再进入步骤 8 |
| 8 | 调用组件 | 标准组件装配 | `page-templates.md` + 组件文档 | 无组件 → 提缺口，不重写 |
| 9 | UI 落地 | 视觉符合设计规范 | `design-tokens.md` / `page-layouts.md` / `pc-ux-principles.md` | 密度或层级不达标 → 按 PC 基线调整 |
| 10 | 设计校验 | 八维自检报告 | `design-review.md` | 有阻塞项 → 修完再交付 |

**步骤 3–7 是本次升级新增的决策环节。** 步骤 1 的产物是步骤 2 的输入，以此类推；后续步骤不得跳过前序结论自行假设。

## 二、产品理解八问

用户只给一句话（如「做一个城市业务拓展系统首页」）时，不要直接开始拼页面。先回答八个问题：

| # | 问题 | 为什么问 | 无答案时怎么办 | 输出到 |
|---|---|---|---|---|
| 1 | 用户是谁 | 决定信息密度、术语深度、默认筛选 | 按业务域推断最常见岗位，标为假设 | 卡·用户 |
| 2 | 使用场景是什么 | 决定进入方式、首屏重点、任务连续性 | 办公室 PC + 长时间作业为默认 | 卡·场景 |
| 3 | 用户要完成什么任务 | 决定页面类型与结构顺序 | 从需求动词推断（看/查/录/批/审） | 卡·任务 |
| 4 | 核心业务目标是什么 | 决定指标与优先级 | 归到「效率 / 准确 / 合规 / 时效」之一 | 卡·目标 |
| 5 | 页面解决什么问题 | 决定去掉哪些内容 | 若答不出，说明该页可能不该存在 | 卡·定位 |
| 6 | 处于什么业务流程 | 决定状态、上下游字段、跳转 | 询问或按生命周期推断 | 卡·流程位置 |
| 7 | 进入之前做了什么 | 决定筛选默认值、上下文承接 | 按上游页面推断 | 卡·来路 |
| 8 | 完成之后去哪里 | 决定成功反馈与去向按钮 | 默认「返回列表 + 新记录入列」 | 卡·去路 |

八问的结论必须体现在**页面结构**上，否则等于没问。例：

- 「用户每天来查异常 → 首屏放待办/预警，而不是放装饰性图表」
- 「进入前刚在某合同详情页 → 默认按该合同筛选，并显示可清除的筛选 chip」

### 典型示范（模糊需求）

需求：「做一个城市业务拓展系统首页」

| 维度 | 结论 |
|---|---|
| 用户 | 城市业务拓展人员（执行）、城市负责人（管理） |
| 任务 | 看进展、发现异常、跟进项目、录入新项目 |
| 核心信息 | 项目数量与阶段分布、业绩达成、待办、风险预警 |
| 高频操作 | 新增项目、查看项目、跟进、筛选 |
| 核心路径 | 看概况 → 定位异常 → 进入项目 → 执行动作 |
| 结构结论 | 指标摘要 + 预警/待办 + 项目阶段分布 + 最近项目列表；**不是**一堆图表平铺 |

## 三、角色与权限矩阵

多角色系统必须先建矩阵，再决定页面可见性与主操作。

| 项目 | 说明 |
|---|---|
| 角色定义 | 按「业务职责」分，不按部门名分（例：经办人 / 审核人 / 财务 / 管理员） |
| 典型任务 | 每角色 1–3 个高频任务，作为首屏依据 |
| 可见范围 | 数据范围（本人 / 本组织 / 全量）+ 字段范围（哪些字段不可见） |
| 首屏 | 不同角色是否需要不同首屏；不需要则说明理由 |
| 主操作 | 每角色每页的主按钮分别是什么（唯一） |
| 权限表现 | 无权限时：菜单隐藏 / 页面 403 / 按钮禁用 / 按钮隐藏——**必须明确选一种** |

**权限表现选择规则：**

- 菜单级无权限 → 隐藏菜单项（不显示灰项，减少噪音）
- 页面级无权限 → 独立无权限页（`空状态` 语义，非 404）
- 操作级无权限 → 无权限时**隐藏**；「暂时不可用」（如状态不允许）时**禁用 + 原因**。二者不得混用。

## 四、任务流与来路去路

每条主任务流必须写明闭环，不允许只有 happy path：

```
来路（从哪进入、带什么上下文）
  → 主路径（步骤序列）
  → 分支（改条件、跳步、返回修改）
  → 异常（失败、无权限、校验不过）
  → 去路（成功后去哪、状态如何变化、是否可撤回）
```

**检查项：**

- 每个页面至少有一条来路、一条去路；「只能靠重置页面回到」视为断点
- 返回时必须保留上下文（筛选条件、滚动位置、页签）
- 成功后必须给出：结果标识（单号/编号）+ 状态变化 + 下一步去向

## 五、设计优先级（P0–P5）

| 级别 | 内容 | 冲突时 |
|---|---|---|
| **P0** | 业务逻辑正确 | 与任何其他级别冲突，一律让路。宁可不好看，不可算错 |
| **P1** | 用户任务能顺畅完成 | 不得为了规范/美观打断主路径 |
| **P2** | 信息架构合理 | 不得为了省事把不同性质的内容混进一张表/一个页面 |
| **P3** | 交互效率 | 优先服务高频任务；低频任务可以多一次点击 |
| **P4** | 组件规范 | 有标准组件必须用；组件缺口按流程补，不重写 |
| **P5** | 视觉表现 | 在上述都满足的前提下做好看 |

**裁决示例：**

- 「组件库里没有合适的树选择器」→ 仍在 P4 层：提缺口补组件，**不能**降级成手写结构
- 「为了视觉对称把两个不相关分组塞进同一张卡片」→ 违反 P2，视觉让路
- 「为了 100% 还原原型，把编辑页锚点结构搬到详情页」→ 违反 P1/P2，应重组为查看语义

## 六、主动发现问题

Skill 不只执行需求，还要发现需求里的问题。但**所有新增建议必须同时满足三个依据**，缺一不可：

| 依据 | 含义 |
|---|---|
| 用户任务 | 这个补充服务于哪条具体任务 |
| 业务场景 | 在什么真实场景下会被需要 |
| PC 端效率 | 补充后是否降低了操作次数或错误率 |

缺任一依据 → 不补，最多在交付说明中作为「可选建议」提出。

### 输出格式

```md
### 需求补充建议
- 建议：客户列表增加「状态」列与状态筛选
  - 依据：任务=快速定位停用客户；场景=每月对账前核查；效率=免进详情逐个确认（约 5 次点击/条）
  - 不加的后果：用户需逐条进详情核对
  - 影响：需要后端补 status 字段
```

### 按页面类型的提问清单

| 页面类型 | 该主动确认的点 |
|---|---|
| 列表页 | 搜索、筛选、批量操作、导入导出、状态字段、负责人字段、详情入口、权限控制、删除二次确认、空态文案、数据量级与分页方式 |
| 表单页 | 必填与校验、保存草稿、并发编辑、离开拦截、字段联动、附件与上限、提交后去向 |
| 详情页 | 概览字段（3–5 个）、分组亲近关系、动态记录归属（时间轴）、可执行动作、返回路径 |
| 看板 | 指标定义与口径、时间范围切换、下钻路径、空数据表现 |
| 配置页 | 层级深度、是否影响历史数据、启用/停用语义、变更权限与审计 |
| 审批页 | 审批链、驳回与撤回、加签/转办、批量审批、超时提醒 |
| 多步骤流程 | 步骤数是否合理（每步 ≤8 字段）、可否暂存、可否跳步、返回是否丢数据、提交前校验点 |

**禁止：**

- 无理由加功能（「顺便加个导出」）
- 用「行业惯例」代替业务依据
- 把建议包装成已确认需求直接写进页面

## 七、执行强度（两档）

避免设计层把日常小需求变重。

### A 档 · 设计前置说明卡（复杂需求必须）

**判定为复杂，满足任一：**

- 新建模块或需要判断模块划分
- 涉及 ≥2 个页面
- 需求是一句话、对象或目标不明确
- 涉及角色权限、审批流、状态机
- 存在 ≥2 个未决产品问题（需要用户拍板）

**做法**：先出「设计前置说明卡」并**等用户确认**，再生成页面。卡可以只列关键结论，不必八问全填。

### B 档 · 轻量执行（简单需求）

**判定为简单，全部满足：**

- 单页面，页面类型明确
- 字段来自原型或用户已明确给出
- 无新增角色、无流程变更

**做法**：直接执行；把产品/IA/交互的关键判断写进交付说明的「设计决策」段，不打断用户。

**禁止**：把 A 档需求当 B 档做（尤其「首页 / 工作台」类需求——它天然需要先定任务与信息优先级）。

## 九、常见误判（反例库）

| 误判 | 后果 | 正确做法 |
|---|---|---|
| 看到「首页」就出 Dashboard 图表墙 | 首屏无重点，用户找不到今天该做的事 | 先问任务，按任务排信息优先级 |
| 看到「列表页」就套模板 | 结构正确但任务不闭环（缺批量、缺状态、缺出口） | 先走 `page-type-rules.md` 骨架 |
| 用户说「加个按钮」就加 | 主操作不唯一，操作分散 | 判断按钮层级，收敛为唯一主按钮 |
| 需求含多处重复入口 | 用户不知道该走哪个 | 按 IA 原则合并入口，保留唯一路径 |
| 为展示组件造页面 | 菜单膨胀、无业务意义 | 删除；组件样例页挂在样例区，不进业务 IA |
| 页面只有 happy path | 上线后空态/失败态裸奔 | 按 `interaction-design.md` 状态矩阵补齐 |
