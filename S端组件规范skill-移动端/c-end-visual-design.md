# C端视觉设计层 / C端页面构成规则

> 2025-08 新增，2025-08 二次更正（Page Role 从 T0-T3 四级改为 PR1/PR2/PR3 三级，定义收敛进 `visual-design-reasoning.md`）。这份文件回答的问题跟其他所有参考文件都不一样——不是"这个组件真实不真实""这个 Token 值是多少"，而是**"页面作为一个整体，视觉上像不像一个成熟 C 端 App"**。

> ⚠️ **这份文件现在是 `visual-design-reasoning.md` 的子集，不是平行的另一套规则。** `visual-design-reasoning.md` 定义了完整的设计推理流程（Business Goal → Page Role → ... → Design Critique），这份文件是那个流程里 Visual Strategy 环节（第10节）的具体规则库——背景怎么处理、焦点怎么做、节奏怎么排的执行细则。**Page Role 的权威定义在 `visual-design-reasoning.md` 第2节（PR1/PR2/PR3）**，这份文件不再重复定义，下面直接用 PR1/PR2/PR3。

## 0. 这一层是什么，为什么要单独开一个文件

用户原话："组件使用正确、Token使用正确、移动端规范正确、信息架构基本正确，但视觉结果普遍存在：大量纯白背景、结构过于模板化、一二级页面视觉层级没区别、首页缺少焦点、运营页缺少氛围和节奏、页面像组件拼装、AI过度追求组件复用率牺牲了构图、所有页面都是 NavBar+白底+Card+List 固定模板。"

这段反馈精确指出了一个此前 Skill 里完全空白的维度：`component-library.md`/`page-patterns.md` 回答的是"每个模块该用什么组件""几个模块按什么顺序摆"，但从没回答过"这些模块摆在一起之后，页面看起来是不是有设计感"——**组件正确 + 顺序正确 ≠ 构图有设计感**，这是两件不同的事，之前的 Skill 只做对了第一件。

**这一层的性质说明（重要，不能跳过不看）**：下面这些规则**不是从 Figma 读出来的数据**，BEP-S 的 Figma 源文件本身是静态组件规范画板，没有页面级构图/氛围/节奏的定义，这类判断本来就不存在"标准答案"可查。这份文件是根据用户的明确要求，由 AI 建立的一套页面构成设计判断规则，性质上跟 `interaction-adaptive-tokens.json`（外部标准）、`missing-components.json`（AI兜底方案）都不一样——它不冒充 Figma 规范，也不是"缺组件时的将就方案"，是这个 Skill 主动承担起来的一层新职责：**页面构图判断**。生成页面时如果用到这里的建议，`data-bep-status` 统一标 `AI_DESIGN_DECISION`（不是 `AI_PROPOSED`——`AI_PROPOSED` 用于"组件缺失时的替代方案"，这里没有组件缺失，是构图层面的主动设计判断，性质不同），并在报告里说明依据的是这份文件的第几节规则。

**这一层不改变、不覆盖任何现有红线**：
- BEP-S 真实组件依然优先于一切手搭方案
- Token 依然优先于任何新配色/新数值
- 不允许因为"要做出设计感"就发明新组件，或者把两个真实组件拼出一个库里没有的四不像
- 不允许修改真实组件本身的任何属性
- 移动端基础规范（安全区、点击热区、行高等）必须满足，不能为了视觉效果牺牲
- 组件缺失依然要走 `missing-components.json` 流程如实标记，不能因为这一层强调"设计感"就默许悄悄拿假组件顶替

这一层解决的是**现有真实组件和真实 Token 怎么被组织、被摆放、被赋予视觉层次**，不是"用什么"，是"怎么排"。

## 1. 页面分级：视觉投入度必须分级，不能一刀切

Page Role（PR1/PR2/PR3）的完整定义见 `visual-design-reasoning.md` 第2节，这里只给出这一层最关心的落地映射：

| Page Role | 典型页面 | 视觉投入度 | 背景策略 | 构图自由度 |
|---|---|---|---|---|
| **PR1** | App 首页、Tab根页面、频道首页、大促页、活动落地页、专题页 | 最高——必须有视觉焦点，允许突破"卡片堆叠"的常规排布，鼓励沉浸式/满版背景 | 禁止纯白到底，必须有色块分区/渐变/焦点模块背景 | 最高——图文比例、模块大小可以不均匀，不受"标准页面结构"约束 |
| **PR2** | 列表页、分类页、搜索结果页、详情页、信息流/推荐页、数据看板 | 较高——需要编排节奏，避免单一卡片重复堆叠，但不需要 PR1 那么强的氛围感 | 白底为主但需穿插图片/色块打破单调 | 中——卡片大小/比例可以有变化（大小图混排），但不能牺牲可读性/效率 |
| **PR3** | 表单页、编辑页、设置页、确认/操作类页面 | 低——效率优先，"组件拼装"式的规整排布在这一级是**正确**的，不需要额外加视觉修饰 | 白底/`color.fill.1` 完全没问题，这是这一级该有的样子 | 低——保持组件库既有的规整结构，不需要额外设计 |

**一句话判断**：PR1（首页、运营活动页）要"像一个被精心设计过的展示面"；PR2（列表/详情/推荐/看板）要"像一份被高效编排过的内容流"；PR3（表单、设置、操作这类工具性页面）要"像一个高效的功能界面"——**PR3 保持组件化、规整、可预测是对的，不要给 PR3 强行加视觉修饰**，问题只出在把 PR1/PR2 也做成了 PR3 的样子。生成页面前先判断 Page Role，答案直接决定要不要往下看本文件剩下的章节——如果是 PR3，本文件到这里就结束了，正常走 `page-patterns.md` 的模板即可（`visual-design-reasoning.md` 里也是同样的判断，两处保持一致）。

## 2. 背景与留白策略：跳出纯白（解决"大量使用纯白背景"）

这条只对 PR1/PR2 生效，PR3 维持现状（`color.fill.1` 页面背景 + 白色卡片是正确的）。

### 2.1 可用的真实 Token 组合出的背景策略（不引入库外颜色）

- **色块分区（Zone Background）**：不同模块用不同的背景色分区，不是整页统一 `color.fill.1`。比如首页顶部一个区域用 `color.brand.1`（6%透明度品牌色）打底，营造"这一块是重点区域"的视觉暗示，下面内容区再切回 `color.fill.1`。分区边界不需要生硬的直线分隔，可以用色块本身的渐隐过渡。
- **渐变背景（Gradient）**：只用已有的真实 Token 组合渐变，不引入新颜色。常用组合：`color.brand.3` → `color.fill.1`（品牌色到页面背景色的渐隐，适合首页顶部/Hero区域背景，让 NavBar 区域不再是突兀的一块纯白）、`color.brand.3` → `color.brand.1`（同色系深浅渐变，适合活动页氛围背景）。CSS 写法示例：`background: linear-gradient(180deg, var(--color-brand-3) 0%, var(--color-fill-1) 100%)`。
- **满版图片/插画背景**：首页 Hero 区域、活动页头图，允许用一张背景图片替代纯色。**这类图片素材本身不是 BEP-S 组件库的一部分**，必须标注 `data-bep-status="AI_PROPOSED"`（图片内容）+ `data-bep-note` 说明"此处为构图占位图，非 BEP-S 真实素材，需业务方替换为真实活动图"，不能让人误以为这是库里的真实资源。
- **卡片穿透 / 满版模块**：不是所有内容都要塞进"卡片+16px边距"的标准容器，PR1 允许某个模块的背景色/图片直接铺满到页面左右边缘（不留 `spacing.page.marginX` 的 16px 边距），跟旁边保持在卡片容器里的模块形成对比，制造视觉节奏——这也是"页面像组件拼装"的直接解法之一：所有内容都规规矩矩地塞在同样宽度的卡片里，才是"拼装感"的来源。

### 2.2 禁止行为

- 不允许为了"背景好看"引入 Token 表里没有的新颜色——渐变/分区都必须基于 `design-tokens.json` 里已经存在的颜色值组合，最多调整透明度。
- 不允许把 PR3（表单/设置）也套上渐变背景——那类页面纯白/`color.fill.1` 是正确的效率优先选择，加了反而违和。

## 3. 首页视觉焦点规则（解决"首页缺少视觉焦点"）

每个 PR1 首页/频道页/活动页，**第一屏必须有且只有一个明确的焦点模块**（对应 `visual-design-reasoning.md` 第6节 User Attention Model 的 Primary Visual Focus），视觉权重要明显高于其余模块。

- **焦点模块的位置**：紧跟在 NavBar/搜索栏之下，金刚区（宫格入口）之上——用户第一眼看到的就是这个模块。
- **焦点模块的构成**：可以是 Banner/轮播卡片（复用真实 Card 或规范画板记录的 Carousel 组件，如果 Carousel 是 `NOT_FOUND`，走 `missing-components.json` 流程手搭，不能假装是真实组件）、也可以是一个放大版的重点内容卡片（比如"本月最值得关注的一条"），关键是**视觉体量必须明显大于金刚区下面的普通列表卡片**——高度建议是普通列表卡片的 1.5-2 倍量级（比如普通 Cell 行高 48-60px，焦点模块给到 120-160px 量级），这个具体数值是 AI 设计判断，不是 Figma 规范，报告里要如实声明。
- **视觉权重表达方式**：尺寸更大 + 背景更突出（用第2节的渐变/图片背景，不是白底）+ 位置更靠前，三者至少占两个，不能只靠"放在最上面"这一个维度就说自己是焦点。
- **金刚区本身的规则**：已经在 `component-library.md` 第5节 Grid 和 `icon-library.md`「金刚区专用规则」里有单独规定（彩色 Solar Icons、不能用线性单色图标），这条不重复，焦点模块规则是金刚区规则**之上**新加的一层，两者不冲突——金刚区解决"入口图标好不好看"，这一节解决"整个首页有没有第一眼抓手"。

## 4. 运营/活动页节奏编排规则（解决"缺少氛围、内容编排和视觉节奏"）

PR1 里的活动页跟首页/PR3 功能页最大的区别：**活动页是按"内容策展"逻辑编排的，不是按"组件复用"逻辑编排的**。这一节的规则本质是提醒：不要用做 PR3 页面的思路（打开 `component-registry.json`，一个个查组件往上堆）去做活动页。

### 4.1 节奏 = 模块之间的密度/尺寸/背景要交替变化，不能均质

具体的密度分层（High/Medium/Low）和节奏交替规则（Large→Small→Medium→Large 等）已经收敛进 `visual-design-reasoning.md` 第13-14节（Spatial Design / Visual Rhythm），这里不重复，只强调活动页场景下的三个具体手法：

- **密度交替**：不要让所有模块都是同样信息密度的卡片。高密度模块（比如商品网格、多条优惠信息堆叠）后面接一个低密度模块（比如一整块大图 + 一句slogan文案），密度上的松紧交替本身就是"节奏感"的来源。
- **背景交替**：参考第2节的色块分区，活动页非常适合每个"内容板块"用不同的背景色/渐变区分开，而不是整页一个背景色到底。
- **图文比例交替**：不要所有模块都是"图标+文字"的固定比例，允许某个模块整块是大图（无文字或文字压在图上），跟其它文字为主的模块形成对比。

### 4.2 氛围色的使用边界

活动页经常需要跟活动主题绑定的强调色（比如大促页用红色系氛围，即使 BEP-S 品牌色是青绿色）。这种情况：

- 优先看这个氛围色是否能用 `design-tokens.json` 里已有的语义色（`color.danger.*`/`color.warning.*` 等）表达，能覆盖就不要另开新颜色。
- 如果业务明确需要一个 Token 表里完全没有的活动专属色，必须标 `AI_PROPOSED`，在报告里明确写"这是活动专属配色，不是 BEP-S 全局 Token，仅限本活动页使用，不要把这个颜色带到其他页面"——这条是防止"一个活动页引入的野色值"以后被误当成新的全局规范到处传播。
- 不允许因为要做氛围色，就替换掉 `color.brand.*` 这类全局品牌色本身的定义——氛围色是局部叠加，不是全局覆盖。

## 5. PR2 页面编排规则（列表/详情/搜索/推荐/看板）

> ⚠️ 2025-08 更正：PR2 的范围比旧版 T2 更大——旧版把列表/详情/搜索归进 T3（跟表单/设置同一级，视觉投入度"低"），这次拆开了：**列表/详情/搜索/看板这类"浏览型"页面属于 PR2，需要基本的节奏感；只有表单/编辑/设置这类"操作型"页面才是 PR3**。原因是浏览型页面虽然不需要 PR1 级别的氛围营造，但完全套用 PR3 的规整死板结构，同样会显得"像组件拼装"——用户在浏览时是需要一点视觉节奏来降低阅读疲劳的，跟填表单时追求的"越快越好、越规整越不容易出错"是两种不同的心理状态。

- **卡片不要整齐划一**：信息流/推荐列表允许卡片大小不均匀（比如双列瀑布流里，图片比例不同导致卡片高度自然不同），不要为了"整齐"强行把所有卡片裁成同一个高度——真实 C 端 App 的推荐流很少是整齐的等高网格。
- **穿插非卡片内容**：纯卡片堆叠是"组件拼装感"最常见的来源之一，内容流里适当插入一条"分类导航条""专题横幅""编辑推荐语"这类非标准卡片模块，打破单一节奏。
- **列表/详情页也适用**：不是只有信息流/推荐页需要节奏——订单列表、任务列表这类纯功能性列表，也可以在列表头部加一个统计概览模块（不同密度/不同背景），或者让状态紧急的条目视觉上更突出，不需要所有列表项完全等重——这不代表要牺牲效率，是在效率优先的前提下依然保留基本的层次感。
- **看板（Dashboard）**：数据密度天然较高，节奏交替主要体现在"核心KPI数字（大、突出）→图表（中等密度）→明细列表（高密度）"这样的层级递进，不需要额外加装饰性视觉元素。
- **仍然要遵守组件真实性规则**：卡片本身的样式（圆角/是否有描边投影等）依然要遵守 `component-library.md` 里 Card 的既有规则，"不均匀"指的是布局排布上的大小/间距变化，不是说可以随意修改卡片组件自身的视觉规范。

## 6. "组件复用率 vs 视觉设计"冲突时，视觉构图优先（解决"过度追求组件复用率牺牲构图"）

`SKILL.md`「核心原则」和 `visual-design-reasoning.md` 第16节已经把这条列为正式原则："组件复用率是元素级指标，不是页面级指标"——这里是那条原则在视觉构图场景下的具体判断方法：

> **组件复用率是元素级指标，不是页面级指标。** 单个按钮、输入框、标签、图标，应该优先复用真实组件——这条不变。但页面级的"模块顺序、模块大小、模块间距、背景处理、视觉焦点"，不受"复用率"这个指标约束。不能因为"某个构图方案会用到更多真实组件、复用率数字更好看"，就放弃一个视觉效果更好但复用率稍低的方案。

**判断方法**：如果发现自己在两个方案之间犹豫，其中一个是"每个模块都严格对应一个 Registry 里的真实组件，看起来复用率很高，但页面整体是一排等高卡片"，另一个是"绝大多数元素依然是真实组件，只是模块尺寸/背景/间距做了PR1/PR2允许的变化，复用率统计数字可能会因为多了一两个 AI_DESIGN_DECISION 的构图元素而略低"——**选后者**。复用率是过程指标，不是目标本身，目标是页面本身的设计感和信息传达效果。

## 7. "组件拼装感"自诊断（解决"页面像组件拼装，不像成熟C端App"）

生成 PR1/PR2 页面后，用这几条快速自检有没有"拼装感"（更完整的 Design Critique 流程见 `visual-design-reasoning.md` 第17节，这里是轻量版，两者不冲突，Design Critique 覆盖面更广）：

- [ ] 页面里所有卡片宽度/高度是不是完全一致？（是→拼装感强烈信号）
- [ ] 页面背景从头到尾是不是只有一种颜色（纯白或单一 `color.fill.1`）？（是→拼装感强烈信号，见第2节）
- [ ] 页面里模块之间的间距是不是全部使用同一个 Spacing Token（比如全是12px）、没有任何疏密变化？（是→缺乏节奏，见第4节）
- [ ] 整个页面有没有任何一处"图片"或"非卡片形态"的视觉元素？（完全没有→大概率是拼装感，见第3/4/5节）
- [ ] 第一屏是否存在一个视觉上明显比其他内容更突出的模块？（PR1页面如果没有→缺少焦点，见第3节）

**这五条只适用于 PR1/PR2**，PR3 功能页出现"卡片等宽、背景统一、间距一致"是正常且正确的，不要拿这份清单去"修正" PR3 页面——那样反而是画蛇添足，违反了第1节的分级原则。

## 8. 反模板化规则（解决"所有页面都是 NavBar+白底+Card+List 固定模板"）

`page-patterns.md` 里的页面结构模板（List/Detail/Form/Search/Dashboard/Home/Settings/Empty）+ 新增的 Composition Pattern 库，描述的是**页面/模块结构**（有哪些模块、什么顺序、怎么组合），这份文件描述的是**视觉构成**（这些模块怎么被组织出层次感）——两者必须一起用，只套用结构模板而不看这份文件，就是"NavBar+白底+Card+List"模板化问题的直接成因。

具体规则：

- `page-patterns.md` 的 **Home Page** 模板落地时，必须同时执行本文件第1节（判定为PR1）、第3节（焦点模块）、第2节（背景策略）——不能只搭出"SearchBar+Carousel+Grid+TabBar"的结构就算完成，结构对了不代表构图对了。
- 遇到运营/活动类需求（`page-patterns.md` 没有专门的页面级模板覆盖，因为这类页面结构本身高度自由，但可以用 Composition Pattern 库里的模块拼），直接进入本文件第1节（判定为PR1）+ 第4节，不要因为找不到对应模板就退回套用 List Page 或 Home Page 的结构。
- List/Detail/Search/Dashboard 这几个模板对应 **PR2**，套用模板结构后要额外执行本文件第5节（不需要 PR1 级别的氛围投入，但要有基本节奏）。
- Form/Settings 这两个模板对应 **PR3**，套用模板结构后**不需要**再额外执行本文件第2-7节的构图规则——这些页面保持模板原本的规整结构就是正确答案。
