# PRD → 可点击原型：需求转译规范

> **这份文件解决什么**：产品丢过来一份 PRD（Word / 飞书文档 / 一段粘贴的文字 / 一张原型截图），要直接得到一个可点击的 HTML 设计稿。
>
> **为什么不能"拿到 PRD 就开始画"**：PRD 是**业务语言**，写的是"要能导出报表""支持多级审批""参照 XX 页面"；设计稿要的是**屏幕语言**——几屏、每屏放什么、点一下去哪、空的时候显示什么。中间这一步转译如果靠感觉，结果一定是"功能都做了、流程走不通"。
>
> **本文件就是那一步转译的规则**。上游接任何形态的需求，下游固定接 `html-prototype.md`（可点击原型规范）。

---

## 0. 一句话原则

**PRD 里的每个功能点都必须有一个落点，但不必各占一屏。**

- **不能删功能**：原型代表业务需求集合，AI 有信息架构和视觉设计的判断权，**没有删功能的权力**。觉得不该做，只能标"建议弱化/合并 + 理由"，交给产品决定。
- **可以重组**：把 6 个功能点排成 3 屏是正常设计判断，只要每个功能点都能在覆盖率表里指到具体位置。
- **缺信息不阻塞**：问最多 3 个关键问题，其余写进"假设清单"，交付时一次说清。

---

## 1. 输入形态与读取策略

| 输入形态 | 怎么读 | 注意 |
|---|---|---|
| **纯文本 / 粘贴的 PRD 段落** | 直接解析，按段落抽功能点 | 口语化描述里"最好能""顺便"这类词往往是隐含功能，要单独拎出来确认 |
| **文档文件（.md/.docx/.pdf）** | 先抽全文文本，再按"页面/模块"标题切段 | 几十页的 PRD 不要逐字读完再画，先只读**功能清单/流程图/字段表**三部分，其余按需回查 |
| **带原型的 PRD（Figma 链接 / 截图）** | 先抽功能点与字段，**再决定布局** | ⚠️ 原型只是需求的一种表达，**不是设计答案**。不要照抄它的信息架构和模块堆叠——这正是 `visual-design-reasoning.md` 反复强调的"照抄原型 = 组件拼装感"的来源 |
| **口头/会议纪要** | 边问边记，当场落成需求卡 | 口头需求缺字段率最高，务必当场确认"主键是什么、状态有哪几种" |

**读完先做的事**：把 PRD 里所有**动词**（提交、审批、导出、提醒、筛选、批量操作）和**名词性模块**（列表、详情、统计、设置）圈出来，这是功能点的原始清单，后面覆盖率表就按这份清单核对。

---

## 2. 需求卡（Requirement Card）

解析完 PRD，先产出一张需求卡。**八项全填**，填不出来的写 `ASSUMPTION`，不许留空。

```markdown
## 需求卡 · <项目名>

**A. 业务目标**（一句话，PRD 原文依据）
**B. 角色与权限**（谁用；能看到什么、不能看到什么；是否有跨角色流转）
**C. 屏幕清单**（见 §3，先给数量与名称，不写细节）
**D. 主流程**（见 §4，起点→…→终点，含分支）
**E. 每屏内容块**（每屏 3–6 块，写"放什么"，不写"用什么组件"）
**F. 数据字段**（每类对象的字段；至少：主键、状态、标题、时间、负责人）
**G. 状态与边界**（空/异常/加载/禁用/超长/无权限，逐屏标"要/不要"）
**H. 不在本期范围**（PRD 提到但明确不做的；以及你判断该砍但**没砍**、只标了建议的）
```

> E 项只写"放什么"。一旦开始写"用卡片还是用 Cell"，就跳过了设计判断，会让页面退化成组件拼装。

---

## 3. 功能点 → 屏幕：映射规则

### 3.1 核心判据
**一个用户目标 = 一屏。**不是"一个功能点 = 一屏"。

"看有哪些工单要处理"是一个目标（一屏：列表）；"把这条工单处理掉"是另一个目标（一屏：详情 + 操作弹层）。而"筛选""排序""搜索"是达成第一个目标的手段，**不单独成屏**。

### 3.2 必须拆屏（命中任一条就拆）

| 条件 | 例 |
|---|---|
| 用户目标不同 | 查看 vs 编辑 vs 审批 |
| 进入路径不同 | 从首页进 vs 从消息进 vs 扫码进 |
| 权限不同 | 领班能改、保洁只能看 |
| 单屏模块 > 5 个 | 超过就是该拆了，别硬塞滚动 |
| 返回目标不同 | 详情返回列表 vs 详情返回首页 |

### 3.3 必须合并（命中任一条就合）

| 条件 | 例 |
|---|---|
| 只是补充信息，不构成独立任务 | 工单的"处理记录"放进详情分节，不单开一屏 |
| 必然与主体同时出现 | 统计数字 + 趋势图 = 同一屏的两个模块 |
| 单独成屏没内容可放 | "设置"只有一个开关 → 做成详情页里的一行 |

### 3.4 屏幕清单表（产出物，逐屏一行）

```markdown
| # | 屏名 | 这一屏解决什么 | 对应 PRD 功能点 | 采用范式 | 怎么进来 |
|---|---|---|---|---|---|
| 1 | 工单列表 | 知道有哪些待处理 | 工单列表/筛选/搜索 | P-1 双 Tab 列表 | 首页入口 |
| 2 | 工单详情 | 判断要不要处理、怎么处理 | 工单详情/处理记录 | P-3 分节详情 | 点列表卡片 |
| 3 | 处理弹层 | 选择处理结果并提交 | 处理工单 | P-4 底部弹层 | 详情底部按钮 |
```

**范式列直接引 `page-patterns.md` 的 P-1…P-5**，不要发明新范式；没有匹配的就写"自定义 + 理由"。

### 3.5 屏幕数量控制
- 常规业务需求：**3–6 屏**最合适，能讲清流程又不至于评审时迷路。
- > 8 屏：先确认是不是该拆成两期，或者是不是把"字段"当成了"屏"。
- 1 屏：说明你其实只被要求画个视觉稿，按 `html-prototype.md` 的"单屏视觉稿"分支处理。

## 4. 主流程与状态

### 4.1 主流程（文字连线，够用就行）
```
首页 → 列表 → [点卡片] → 详情 → [处理] → 弹层 → 提交 → Toast → 回列表
                  └→ [筛选无结果] → 空态 → 改筛选 → 列表
```
要求：
- 每条边写**触发动作**（点哪里），不写"进入下一页"这种含糊话。
- 至少标一条**异常分支**（失败/空/无权限）怎么回主流程。
- 断头路必须消灭：每个终点的下一步是什么，要么明确"流程结束"，要么给出口。

### 4.2 状态清单（逐屏，只标"要/不要"）
| 屏 | 空 | 加载 | 失败 | 禁用 | 超长文本 | 无权限 |
|---|---|---|---|---|---|---|
| 列表 | 要 | 可选 | 可选 | — | 要 | 可选 |
| 详情 | — | — | — | 要（无权限时按钮置灰） | 要 | 要 |

> 列表页空态是**必做**（约束 C-86），其余按业务是否真实存在决定，不要为了"完整"硬造。

## 5. 缺口处理：3 个问题 + 一张假设清单

### 5.1 什么值得问（最多 3 个）
只有**不问就会整屏画错**的才问：

- 角色是谁、有几级权限（决定屏数和可见性）
- 核心对象的状态有哪几种（决定筛选、Tag、可执行动作）
- 有没有必须严格对齐的老系统/老入口（决定信息架构能不能动）

### 5.2 什么不问，直接写假设
影响单个字段、单个文案、单个次要按钮的，一律写假设，不要打断产品。

假设清单格式（**必须四列**）：

```markdown
| # | 假设 | 依据 | 影响范围 | 若要改，改哪里 |
|---|---|---|---|---|
| 1 | 处理结果只有"已保洁/需整改/非本单"三选 | PRD 提到三种处置动作，未给全集 | 处理弹层选项 | 弹层 `.sheet-body` 的选项数组 |
| 2 | 提交后回列表而非留在详情 | 同类工单系统惯例，PRD 未写 | 提交后的跳转 | `data-sheet-submit` 分支 |
```

### 5.3 禁止的"缺信息处理"
- ❌ 因为没写就不做这个功能（等于删业务能力）
- ❌ 自己编一个业务规则当规范（要编就写进假设清单，标明是自己的判断）
- ❌ 连问 8 个问题把产品问烦（超过 3 个就说明该先按假设做一版给他看）

## 6. PRD 覆盖率核对表（强制，不可省）

交付前必须出这张表。**PRD 里每个功能点一行**，原文引用，不许概括。

```markdown
| # | PRD 原文功能点 | 落点（屏 + 模块） | 处理 | 说明 |
|---|---|---|---|---|
| 1 | "支持按状态筛选工单" | 列表 · 顶部胶囊 | 已实现 | 3 个状态 |
| 2 | "可批量指派给保洁班组" | 列表 · 卡片操作行 | **弱化** | 一期单条指派，批量排在二期（建议，待确认） |
| 3 | "导出月度报表" | — | **本期不做** | 已与产品确认移出范围 |
```

规则：
1. 覆盖率 < 100% 不许交付，除非每一处缺口都写了"本期不做 + 谁确认的"。
2. "弱化/合并"必须写理由，且**只能建议，不能自己定**——交付时单独列出来给产品拍板。
3. PRD 里含糊的表述（"参照 XX""类似 YY"）不许自己解读完就算数，要么问，要么进假设清单。

---

## 7. 与既有报告的关系

PRD 场景下，Step 6 的八块报告**照常出**，但前面追加三块：

```
① 需求卡（§2）
② 屏幕清单表（§3.4）
③ PRD 覆盖率核对表（§6）
④–⑪ Step 6 原有八块（Design Reasoning Summary … Validation）
⑫ 假设清单（§5.2）
```

不要因为"PRD 已经写清楚了"就省掉 Design Reasoning 和 Design Critique——PRD 定义的是**做什么**，不是**怎么排**。

---

## 8. 交付形态

PRD 场景**默认交付多屏可点击原型**：

- 走 `html-prototype.md` 全流程（单文件零依赖 / 手机壳 / hash 路由 / 12 条交互契约 / 状态覆盖）。
- 必附三段说明：**怎么打开 / 能点通什么 / 没做什么 + 假设了什么**。
- 覆盖率表和假设清单**同时贴进回复**，不要只放在文件里——产品评审第一眼要看的就是"我提的都在不在"。

---

## 9. 给产品的一页版 PRD 模板（推荐，非强制）

PRD 写得越接近这张表，出稿越准、来回越少。**没有也能做，但会多一轮假设确认**。

```markdown
【项目名】
1. 背景与目标：为什么要做，成功的样子是什么
2. 角色：谁用，权限差别
3. 页面/流程：用户从哪进、经过哪、到哪结束（有流程图最好）
4. 每页要放什么：3–6 条，写"放什么"不用写"长什么样"
5. 数据字段：对象有哪些字段，哪些必填
6. 状态：对象有哪几种状态，每种状态能做什么操作
7. 边界：空的时候显示什么、失败怎么办、没权限怎么办
8. 不在本期：明确不做的，避免被当成漏做
9. 参考：老系统/竞品截图（说明"参考哪一点"，不要只说"参照这个"）
```

## 10. 反模式（这几条一出现，出稿必翻车）

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| 把 PRD 每句话做成一屏 | 8 屏以上、流程断裂 | 按"用户目标"归并，见 §3.1 |
| 照抄 PRD 附带原型截图的信息架构 | 页面像组件拼装、没有设计判断 | 抽功能点后重新做 Page Composition |
| PRD 说"参照 XX 页面"就直接照做 | 抄错对象（XX 可能是旧版/别的业务） | 问清"参考它的哪一点：布局？字段？交互？" |
| 字段表缺失就自己编字段 | 数据对不上，开发返工 | 用最小字段集（主键/状态/标题/时间/负责人）+ 标假设 |
| 缺信息就少做一个功能 | 评审时被判"漏做" | 做出来 + 标假设，或明确写"本期不做（待确认）" |
| 交付只说"做好了" | 产品不知道能点哪里、哪些没做 | 三段说明 + 覆盖率表 |
