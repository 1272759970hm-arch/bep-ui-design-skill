# AI Design Brain（AI 设计决策层）

> 2025-08 新增，2025-08 二次扩容为 "AI Design Brain"。这是这个 Skill 里级别最高的一层——不是"再补一条视觉规则"，是**改变生成页面时的思考顺序本身**。之前所有规则（`component-library.md`/`design-tokens.md`/`c-end-visual-design.md`）回答的都是"这个东西该怎么做/该长什么样"；这份文件回答的是"在做任何一个'该怎么做'的判断之前，应该先想清楚什么"。

> ⚠️ **文件名保留不变，但这次扩容之后它的定位是 "Product + UX/UE + UI + BEP-S Design System"，不再只是"视觉设计推理"。** 之所以不改文件名、不拆成多个新文件——把"这个 Skill 该怎么思考"的规则拆成一堆碎片文件，本身就会重蹈"页面像拼装"的覆辙，规则文件也不该是拼出来的。

## 0. 为什么需要这一层：诊断"组件拼装感"的根因

之前的生成流程本质上是：**需求 → 查组件 → 拼组件 → 生成**。这个流程里，"组件映射"（Step 4）是第一个、也几乎是唯一一个需要主动判断的环节——只要每个模块都能在 `component-registry.json` 里查到对应条目、Token 都取对了，流程就"顺利走完了"。

第一次扩容（本文件早期版本）解决了"页面构图有没有设计感"，但还留了一层更上游的空白：**AI 只会照着原型的功能做 UI 映射，没有主动判断信息架构合不合理、功能优先级该怎么排、这个页面到底需要多少设计自主权**——这是产品经理和 UX 设计师的思考范畴，不是视觉设计师能单独补上的。这次扩容补的就是这一层：**Product Thinking → Information Architecture 重组权限 → UX/UE Thinking**，全部排在 Visual Hierarchy 之前。

**核心原则，写在最前面，后面所有章节都是这一句话的展开**：

> **先做产品判断，再做设计判断，最后选组件（Product First, Then Design, Then Select Components）。** 原型不是最终设计，原型只代表业务需求和功能集合——AI 拥有设计判断权，可以优化信息架构、功能布局、交互和视觉表现，但不能无理由改变业务目标、不能删除业务能力。Component Reuse（组件复用）是约束条件，不是设计目标。

## 1. 完整流程（取代"需求→查组件→拼组件→生成"）

```
User Requirement（用户需求）
  ↓
Product Thinking（业务目标→用户目标→核心任务→核心CTA→功能优先级判断）
  ↓
Page Role（PR1/PR2/PR3）+ Design Autonomy Level（L0-L4）——这个页面是什么角色、AI这次能改多少
  ↓
Information Architecture（信息架构重组，受 Autonomy Level 约束，业务能力不能丢）
  ↓
UX/UE Thinking（任务路径/首屏策略/交互模式/状态设计/高低频功能处理）
  ↓
Visual Hierarchy（视觉层级）——什么最大/最重要/该弱化/该隐藏/该合并/该留白
  ↓
Visual Strategy（视觉策略）——背景/密度/节奏怎么处理
  ↓
Layout Hypothesis（布局假设，至少2个方案）——先出至少两个方案再选
  ↓
Page Composition（页面构成）——用 Composition Pattern 把方案落成具体模块组合
  ↓
Tab Intelligence（如果构成里出现Tab，先判断该不该存在，再决定样式）
  ↓
Component Mapping（组件映射，先判断语义意图再选组件）——这里才第一次查 component-registry.json
  ↓
Token Mapping（Token映射）——具体数值
  ↓
Generate（生成 HTML/CSS）
  ↓
Design Critique（设计自评，含85分强制阈值）——生成后回头检查，不是生成前的自查
  ↓
Refine（低于85分强制回到 Information Architecture 或 Layout Hypothesis 重新来，不是回去改几个 Token）
```

**这条流程在 `SKILL.md` 里的落地方式**：Product Thinking 对应 Step 1；Page Role + Design Autonomy Level 对应 Step 2；Information Architecture/UX/UE Thinking/Visual Hierarchy/Visual Strategy/Layout Hypothesis/Page Composition/Tab Intelligence 全部塞进 **Step 3.5（Design Reasoning）**；Component Mapping/Token Mapping 是 Step 4-5，**位置不变，但在 Step 3.5 产出构图方案之后才做**；Design Critique 对应 **Step 8.5**；Refine 是 Step 8.5 不达标时触发的循环。

**PR3 页面（表单/编辑/设置/操作）的简化路径**：判断出 Page Role 是 PR3 之后，Design Autonomy Level 默认锁定在 L0-L1，Information Architecture 之后直接进 Component Mapping——跳过 UX/UE Thinking 的状态/节奏设计、Visual Hierarchy、Visual Strategy、Layout Hypothesis、Page Composition、Design Critique 这几步。**这不是偷懒，是正确答案**：PR3 页面的设计目标就是"高效、可预测、组件化"，本来就不需要这一层判断（跟 `c-end-visual-design.md` 第1节的分级原则一致）。

## 2. Page Role：PR1 / PR2 / PR3（原 L1/L2/L3 改名，见下方改名说明）

> ⚠️ **改名说明（2025-08）**：这一版新增了 Design Autonomy Level，用 `L0-L4` 表示"AI这次能改多少"；如果 Page Role 继续叫 L1/L2/L3，两套编号会撞在一起、读起来分不清哪个"L"是哪个意思。所以 Page Role 从这一版起改名 **PR1/PR2/PR3**（Page Role 的缩写），`L` 这个字母完整让给 Design Autonomy Level。**这是唯一权威定义**，`c-end-visual-design.md` 里的分级已经按这个改名同步。

| Page Role | 定义：用户是怎么"来到"这个页面的 | 典型页面 | 设计目标 |
|---|---|---|---|
| **PR1** | 用户"到达"这里，不是"点进来"这里——App/角色的主入口、Tab根页面，或者带营销目的、需要主动吸引用户的落地页 | 首页、频道首页、Tab根页面（如"值守台"这类角色主页）、运营活动页、大促页、专题页 | 第一眼抓住注意力、建立视觉焦点、传达"这个页面是关于什么的" |
| **PR2** | 用户带着一个相对宽泛的意图"点进来"，目标是浏览/查找信息，还没有进入具体操作 | 列表页、分类页、搜索结果页、详情页、信息流/推荐页、数据看板 | 高效呈现信息，同时保留基本的节奏感（不是纯粹的效率工具），比 PR1 克制，比 PR3 松弛 |
| **PR3** | 用户带着一个明确、单一的任务来的，通常是"完成一个动作"（填一份表、改一个设置、确认一个操作） | 表单页、编辑页、设置页、确认/操作类页面 | 效率优先，规整、可预测、组件化——**这一级保持"组件拼装"式的规整排布是正确答案**，不需要额外的设计投入 |

**判断方法**：先问"用户是主动'来'这里，还是从别处'点进'这里，还是带着一个具体任务'打开'这里"——依次对应 PR1/PR2/PR3。拿不准时看信息密度和操作性质：偏展示/浏览 → PR1或PR2；偏输入/操作 → PR3。

**和更早版本 T0-T3 的对照**（仅供理解历史决策，新页面直接用 PR1/PR2/PR3）：最早的 T0(首页)+T1(运营活动页) → 合并为 **PR1**；T2(内容/推荐页) → 对应 **PR2**（范围更广，纳入了列表/搜索/详情/看板这类"浏览型"页面）；T3(二级功能页) 里偏"浏览"的部分拆到 **PR2**，偏"操作"的部分留在 **PR3**。中间版本短暂用过 L1/L2/L3，这次因为跟 Design Autonomy Level 撞号，改成 PR1/PR2/PR3。

## 3. Design Autonomy Level：L0-L4（新增，回答"这次能改多少"）

Page Role 回答"这是什么类型的页面"，Design Autonomy Level 回答"AI 这次有多少权限去改动原型的结构和视觉"——**两者是两个正交的维度，不是一回事**：同样是 PR2 的列表页，用户可能要求"完全照抄原型"（L0）也可能要求"帮我重新设计"（更高等级）。

| 等级 | 定义 | 允许的动作 |
|---|---|---|
| **L0** | 严格还原原型 | 只能做组件真实性替换（原型用的是假组件/手绘图形，换成真实BEP-S组件），结构、顺序、分类、视觉一律不动 |
| **L1** | 结构优化 | 可以调整间距、对齐、視覺细节，不能改模块顺序和分类逻辑 |
| **L2** | UX优化 | 可以调整信息架构（合并/拆分模块、换分类轴、优化Tab/入口），前提是通过第5节的业务能力保留核对 |
| **L3** | 视觉创新 | 在L2基础上，可以引入 Hero/Banner/背景层级/色块等视觉手段建立设计感（`c-end-visual-design.md`的规则） |
| **L4** | 产品级自主设计 | 在L3基础上，可以重新判断功能优先级、重新设计交互路径，允许提出跟原型信息架构完全不同的方案 |

**默认映射（按 Page Role 给默认值，不用户户每次都问）**：

| Page Role | 默认 Autonomy Level | 理由 |
|---|---|---|
| PR1（首页/运营活动页） | L3-L4 | 这类页面的核心价值就是"设计感"和"转化率"，原型往往只是功能占位，AI 应该主动做产品级判断 |
| PR2（列表/详情/推荐/看板） | L1-L2 | 效率和设计感要平衡，允许优化信息架构，但不需要 L1 级别的强烈视觉投入 |
| PR3（表单/设置/操作） | L0-L1 | 效率优先，创造性投入本身就该最低，改动越大越容易破坏用户已经熟悉的操作路径 |

**覆盖规则**：
- **用户明确要求"严格按照原型"时，不管 Page Role 是什么，强制 L0**——这是用户指令，不是可协商的起点，跟其他 `USER_OVERRIDE` 场景优先级一致。
- 用户也可以主动要求把某个页面的 Autonomy Level 往上调（比如一个 PR2 列表页用户要求"帮我重新设计得更有设计感"），这种情况按用户要求的等级走，不受默认映射限制。
- 没有明确指令时，用默认映射，并在 Step 6 报告里说明"本次按 PRx 默认使用 Ly，如果需要更保守/更大胆的设计自由度请告诉我"。

**Autonomy Level 是一个贯穿多层的阀门，不是只管视觉**：它同时约束 Information Architecture（第5节）能不能重组、UX/UE Thinking（第8节）能不能改交互路径、Visual Strategy（第10节）能不能用强烈的视觉手段——L 值越低，这三层能做的事越少，直接跳到"组件真实性替换+照抄结构"。

**不管 Autonomy Level 多高，都不能松动的边界**：见第15节 Visual Design Budget 的三条硬边界（Token/组件/移动端规范），这三条不随 Autonomy Level 变化。

## 4. Product Thinking（产品思维，生成前必答）

在做任何页面结构判断之前，先完成这几步（这是 Step 1 的强制产出，不能跳过，也不能用一句"用户要一个XX页面"糊弄过去）：

1. **业务目标是什么？**（不是"展示订单列表"这种功能性描述，是"为什么业务需要这个页面存在"——比如"让门店值守人员在最短时间内发现并处理异常订单，减少客诉"）
2. **用户目标是什么？**（用户来到这个页面，最重要的任务是什么——一句话说清楚，如果说不清楚一句话，说明需求本身还不够明确，要回去跟用户确认，不能硬着头皮往下走）
3. **核心任务是什么？核心 CTA 是什么？**（页面最希望用户完成什么行为，对应哪个具体的可点击元素——这个答案直接决定后面 Visual Hierarchy 里"什么该是 Primary Focus"）
4. **功能优先级判断**（2025-08新增，这是之前版本缺的一步）：把原型里出现的每一个功能点，标注"前置 / 保持 / 弱化 / 合并"四种处理方式之一，并写明理由：
   - **前置**：跟核心任务直接相关，应该提到更显眼的位置（比如"扫码核销"从原型里"两个统计卡片之后"提到页面最上方，因为它是页面唯一的高频核心动作）
   - **保持**：跟原型的呈现方式/位置差不多合理，不需要特别处理
   - **弱化**：不常用、不紧急的功能，视觉权重应该降低，不能跟核心功能平起平坐
   - **合并**：多个原本分开的功能点，本质上是同一类信息，应该合并展示（比如把"配送异常"和"退款待处理"从两个不同产品类型的统计块里摘出来，合并成一个"立即处理"分组，因为两者都需要人工介入判断，产品类型对这个分组没有意义）

这一步的产出（功能优先级清单）是后面 Information Architecture 重组的**唯一权威依据**——第5节的所有分组/合并/拆分决策，都要能回溯到这张清单，不能是"看着顺眼就这么分了"。

## 5. Information Architecture（信息架构，允许重组，但有红线）

**这一步要主动质疑原型的信息架构合不合理，不是照抄原型的分类方式**——之前一个真实案例：面对"履约工作台"原型（分类轴是"实物商品 vs 数字商品"），第一版重构只是把原型的两个统计卡片挪了挪位置、改了个标签样式，**分类逻辑照抄了原型**，被用户指出"信息架构并没有做设计"。正确的做法是回到第4节的功能优先级判断，用"用户会怎么使用这些信息"重新定分类轴——那次改成了"需要立即处理 / 履约进度总览 / 明细记录"三层，产品类型（实物/数字）从最高层级的分类轴降级成了明细列表里的筛选维度。

**允许的重组动作**（受第3节 Autonomy Level 约束，L2 以上才能做）：
- 调整模块顺序
- 合并原本分开的模块（依据第4节"合并"标注）
- 拆分原本混在一起的模块（比如把"待处理数量"和"记录总数"这两种性质不同的数字拆开，不能同一个网格里既放"退款(2)"又放"全部数字订单(4)"）
- 更换分类轴（比如把"按产品类型分类"换成"按是否需要人工处理分类"）
- 优化 Tab 层级和功能入口（具体判断方法见第9节 Tab Intelligence）

**⚠️ 硬性红线：业务能力保留核对表（不受 Autonomy Level 影响，任何等级都必须做）**

不管 Autonomy Level 多高，**不能无理由删除业务能力**。重组信息架构之后，必须逐条核对：原型里出现的每一个功能点/入口/数据项，在新方案里能不能找到对应位置（哪怕位置、形式、分组方式变了）？

- 找得到 → 在 Step 6 报告里说明"原来在哪、现在在哪、为什么这么调整"
- 找不到 → **这是红线，不能悄悄丢掉**，必须在报告里明确列出"这个功能点在新方案里被省略了，原因是……需要跟你确认是否可以去掉"，不能自己决定删除，只能决定怎么摆放
- 这张核对表本身要作为 Step 6 报告的一部分交付给用户，不是内部自查完就丢掉

**AI 有信息架构的设计判断权，但没有业务功能的取舍权**——这是这次扩容里最重要的一条边界。

## 6. User Attention Model（用户注意力模型）

生成前必须明确分出四层，每一层对应到具体的页面模块：

| 层级 | 定义 | 数量约束 |
|---|---|---|
| **Primary Visual Focus**（主视觉焦点） | 用户视线第一落点，直接对应第4节"核心任务/核心CTA" | **任何页面默认只能有一个**，这是硬性约束，不是建议——如果发现自己列出了两个"焦点"，说明还没想清楚，要重新排优先级 |
| **Secondary Focus**（次焦点） | 视线第二落点，重要但不能跟主焦点抢注意力 | 通常1-3个 |
| **Supporting Content**（辅助内容） | 提供背景信息、上下文，不要求用户立即行动 | 不设上限，但要控制密度（见第13节） |
| **Functional Content**（功能性内容） | 导航、设置入口、辅助操作——用户需要时能找到，不需要时不应该抢视觉资源 | 通常是 TabBar/次要按钮/辅助链接这类 |

对应到 `c-end-visual-design.md` 第3节的"首页焦点模块"：那一节讲的就是 Primary Visual Focus 在 PR1 页面里的具体实现规则（尺寸/背景/位置），这里是更通用的模型，适用于 PR1 和 PR2。

## 7. Visual Hierarchy（视觉层级判断）

对着 User Attention Model 分出的四层，逐一决定：

- **什么最大？**（通常是 Primary Visual Focus，尺寸/留白/背景对比度上要明显区别于其他内容）
- **什么最重要？**（重要不等于最大——次要焦点可能用颜色/位置强调，不一定靠尺寸）
- **什么应该弱化？**（对应第4节标注"弱化"的功能点，用更小字号/更低对比度颜色处理）
- **什么应该隐藏？**（默认收起、点击展开，或者干脆放到二级页面，不是所有信息都要在首屏铺开）
- **什么应该组合？**（对应第4节标注"合并"的功能点，多个独立小模块合并成一个更完整的复合模块）
- **什么应该留白？**（不是所有空间都要塞满内容——留白本身也是一种视觉层级表达，衬托出旁边内容的重要性）

这六个问题没有标准答案，答案必须能回溯到第4节的功能优先级判断——"这么排是因为它被标注为前置"，不能是"这么排看起来比较好看"。

## 8. UX / UE Thinking（用户体验思维，新增）

这一层解决"页面内容排对了，但用起来顺不顺"的问题，之前完全空白，这次补齐：

### 8.1 用户任务路径

把第4节的核心任务拆成具体步骤，检查页面结构是否支持这条路径顺畅走完，不要让用户为了完成一个任务在页面里来回找。比如"扫码核销"这个任务，路径是"打开页面→找到扫码入口→点击→完成"，如果扫码入口被埋在多屏之后，路径就是不顺畅的，这也是判断 Primary Visual Focus 该放哪的依据之一。

### 8.2 首屏策略

第一屏（不滚动能看到的区域）应该覆盖：Primary Visual Focus + 最关键的1-2个 Secondary Focus，其余内容允许滚动查看。不要为了"信息完整"把所有内容硬塞进首屏，导致真正重要的内容被稀释。

### 8.3 高频 / 低频功能差异化处理

第4节的功能优先级判断要结合使用频率：
- **高频功能**（用户每次打开都会用，比如核销、搜索）：应该常驻、易触达，不能藏在二级菜单里
- **低频功能**（偶尔用一次，比如导出、设置）：可以收进"更多"菜单或次级入口，不需要占用首屏视觉资源

不能用"这个功能听起来很重要"代替"这个功能实际使用频率高不高"来判断视觉权重。

### 8.4 状态设计（空状态/异常态/加载态）

每个展示数据的模块，都要考虑三种非默认状态：
- **空状态**：没有数据时展示什么（复用 `component-library.md` 里真实的 Empty 组件，8种插画场景任选语义匹配的，不要留一片空白或者手绘一个新占位图）
- **异常态**：加载失败/网络异常时展示什么
- **加载态**：数据还在请求时展示什么（`mobile-ui-rules.md`"空状态/Loading"章节记录的处理方式：按场景用 Switch/Toast/Picker 各自的"加载中"状态，或 icon-加载 图标）

这三种状态不需要在生成的静态 HTML 里都画出来，但要在 Step 6 报告里说明"这个模块的空状态/异常态按什么方案处理"，不能假装这些状态不存在。

### 8.5 交互模式

复用 `interaction-adaptive-tokens.json` 已有的外部标准（点击热区/hover-按下反馈/动效时长），这一节不重复展开，只强调：UX Thinking 阶段要主动想清楚"哪些元素需要交互反馈"，不要等到 Component Mapping 阶段才被动发现漏了。

## 9. Tab Intelligence（Tab 存在性判断，新增）

`component-library.md`「标签栏 Tab」章节已经有 Tab **该怎么摆**的规则（一级下划线在上、二级胶囊在下、平分宽度等），但那些规则都建立在"已经确定要用 Tab"的前提上——这一节补的是**更前置的一步：这个页面真的需要 Tab 吗**。

**判断标准**：只有满足以下条件才允许使用 Tab——

1. 内容存在**至少2个互斥的分类维度**（一条内容不会同时属于两个Tab）
2. 用户会**主动**想要按其中一个维度筛选浏览（不是"分了类看起来更清楚"这种伪需求）
3. 每个分类下都有**足够支撑独立展示**的内容量（如果某个Tab点开几乎没内容，说明这个分类维度本身站不住脚）

**不满足时怎么办**：
- 只有1个维度、或维度之间不互斥 → 不用 Tab，用一个列表 + 可选的 Filter（筛选器图标/下拉菜单）就够
- 分类内容量差异悬殊（一个Tab下100条，另一个下1条） → 考虑用 Filter chips（跟第5节"信息架构重组"呼应，比如把"产品类型"从原型的顶层大分类降级成明细列表的筛选维度，用二级Tab胶囊承载）而不是平级 Tab

**禁止行为**：不允许为了"页面看起来分类清晰/视觉更丰富"机械地加 Tab——这是新增的一条防呆规则，Tab 是信息架构工具，不是装饰。

**通过判断之后**，才进入 `component-library.md`「标签栏 Tab」章节查具体的样式/摆放规则。

## 10. Visual Strategy（视觉策略）

这一步产出背景处理、密度分布、色彩层级的整体策略，具体规则见 `c-end-visual-design.md`：
- 背景与留白策略 → 第2节
- 首页焦点模块的视觉表达 → 第3节
- 运营/活动页节奏编排 → 第4节
- PR2页面编排规则 → 第5节

这一步不重复展开这些规则，只强调一件事：**Visual Strategy 必须在 Layout Hypothesis 之前定下来**，因为它是评价"哪个布局方案更好"的标准之一——如果没有先想清楚背景/密度/节奏策略，比较两个布局方案时就没有客观依据，容易变成"我觉得这个好看"这种无法验证的判断。**这一步同样受 Design Autonomy Level 约束**：L2 及以下不做强烈的视觉策略介入，维持组件库默认样式。

## 11. Layout Hypothesis（布局假设：强制至少两个方案）

**生成页面前，不允许直接开始画页面。** 必须先针对 Page Composition 提出至少两个候选布局方案，再依据第4节的业务目标选择其中一个——这条是防止"AI 想到第一个能用的排法就直接定稿"的硬性规则。

**格式要求**：两个方案都要用"模块顺序简写"的方式写出来，比如：

```
方案A：Hero → Category → Promotion → Product
方案B：Hero → Product → Promotion → Content
```

然后**必须写一句话说明为什么选了其中一个**，理由要能回溯到第4节的业务目标（比如"方案A更适合，因为业务目标是提升品类渗透，需要把品类导航放在促销信息之前"），不能只说"方案A更好看"。

**这一步的产出必须写进 Step 6 报告的 Design Reasoning Summary 部分**，把没选的方案也列出来、连同选择理由——这是给用户审核设计判断的关键材料，不能只交付最终方案、藏起没被选中的那个，那样用户没法判断这次设计决策是不是靠谱。

**PR3 页面、或 Autonomy Level 在 L1 及以下时，不需要这一步**（见第1节）。

## 12. Page Composition 与 Composition Pattern（组件组合方式，不是组件本身）

**Composition Pattern（构成模式）** 是"几个真实 BEP-S 组件 + 文本/图片/容器/间距，按固定方式组合出的一个可复用页面模块"——**它不是组件，不进 `component-registry.json`，也不需要在 Figma 里有对应的东西**。完整的 Composition Pattern 清单和具体组合公式见 `page-patterns.md`「Composition Patterns」章节，这里只讲使用规则：

1. **组合的原材料必须都是已有的东西**：真实 BEP-S Component（Card/Button/Tag等）+ 纯文本 + 图片（如果需要，按 `c-end-visual-design.md` 第2节的规则，标注清楚是否为占位图）+ 容器（div/section 这类没有语义、纯粹用来做布局的元素）+ 间距（Spacing Token）。**不允许在组合过程中修改任何真实 Component 本身的属性**。
2. **Page Composition 这一步的产出是"这个页面由哪几个 Composition Pattern 按什么顺序组成"**，这个清单直接对应 Layout Hypothesis 里选中的那个方案。
3. **Component Mapping（Step 4）在这一步之后才开始**：有了 Composition Pattern 清单，才知道每个 Pattern 内部具体需要哪些真实组件，这时候才去查 `component-registry.json`——顺序不能反过来。

## 13. Spatial Design（空间设计：密度分层）

页面不能所有区域保持相同密度。定义三个密度层级（具体数值见 `design-tokens.json` 的 `aiProposedExtra.spacing.density.*`，都是从已有 Spacing Token 派生的倍数关系，不是凭空定的新数字）：

| 密度层级 | 典型间距 | 适用场景 |
|---|---|---|
| **High Density**（高密度） | 沿用现有 `spacing.module.gap`(12px) 或更紧凑 | 数据密集的表格/清单/五宫格这类需要一屏容纳较多信息的模块 |
| **Medium Density**（中密度） | 现有间距的1.5倍量级 | 常规卡片流 |
| **Low Density**（低密度） | 现有间距的2倍量级 | Hero/焦点模块前后、需要让用户视线停留/呼吸的区域 |

**规则**：一个 PR1/PR2 页面里，高中低三档密度至少要出现两档，不能从头到尾只用一档密度——这是"组件拼装感"最容易暴露的地方之一。

## 14. Visual Rhythm（视觉节奏）

页面需要产生节奏，具体表现为模块的尺寸/性质要交替变化，不能持续重复同一种模式：

**允许的节奏模式**：
- 尺寸交替：`Large → Small → Medium → Large`
- 性质交替：`Visual → Functional → Visual → Functional`

**禁止的模式**：
- `Medium → Medium → Medium → Medium`（连续超过3个同质模块，是"组件拼装感"的直接来源）

**检查方法**：把页面从上到下的模块列一个序列，标出每个模块的"尺寸档位"和"性质"，如果连续3个以上模块的档位和性质都相同，就要回到 Layout Hypothesis 重新排布。

## 15. Visual Design Budget（视觉设计预算）

不同 Page Role 拥有不同的"设计自由度"（跟第3节 Autonomy Level 共同决定，Page Role 给基础预算，Autonomy Level 是这次实际批准使用多少）：

- **PR1 页面拥有最高的视觉设计自由度**：背景层级、图片/Hero、大标题、内容模块组合、空间关系、色彩层级、内容密度变化，具体规则在 `c-end-visual-design.md` 第2-5节。
- **PR2 页面自由度中等**：允许卡片大小不均、穿插非卡片模块，但不需要 PR1 级别的强烈氛围处理。
- **PR3 页面自由度最低**：保持规整的组件化结构就是正确答案。

**不管自由度多高，都必须遵守三条边界（不可协商，不随 Autonomy Level 变化）**：
1. 只能用 `design-tokens.json` 里已有的 Token 做组合，不能引入库外新值——除非明确标注 `AI_PROPOSED` 并说明。
2. 只能用真实 BEP-S Component 做 Composition Pattern 的材料，不能新建组件、不能修改真实组件属性。
3. Mobile UI Rules（安全区/点击热区/行高等）必须满足，不能为了视觉效果牺牲可用性。

**明确禁止的行为**：随机渐变、随机颜色、随机阴影、无意义装饰（不服务于 Visual Hierarchy 判断、纯粹为了"看起来更丰富"添加的图形元素）。**"设计自由度更高"不等于"可以不遵守 Token/组件规则"**，自由度高的是"怎么组合、能不能重组信息架构"，不是"可以突破材料边界"。

## 16. Component Reuse Principle（组件复用原则）+ Component Intelligence（组件选择方法论）

> **Component Reuse is a constraint, not the design objective.**（组件复用率是约束条件，不是设计目标。）

- **元素级**（单个按钮/输入框/标签/图标）：应该优先复用真实组件，这条不变。
- **页面级**（模块顺序、模块大小、模块间距、背景处理、视觉焦点）：**不受复用率约束**。
- **禁止行为**：为了拉高 Component Reuse Score 而堆叠组件；为了让每个模块都能对应一个真实组件，牺牲更好的构图方案。

**Component Intelligence（2025-08新增）——"先判断设计意图，再选组件"，不是"看到一个功能，找一个组件"**：这条方法论的完整版本和案例（比如"到店自提"该用 PROPERTY_TAG 性质的普通标签，"待备货"该用 STATUS_TAG 性质的状态角标）在 `component-library.md`「Component Intelligence」章节，这里只强调原则本身——**每一个组件选择，都要先回答"这条信息的语义意图是什么"，再去匹配哪个真实组件承载这个意图**，不能反过来看见一段文字信息就顺手套一个视觉相似的组件。这条跟本节的 Component Reuse Principle 是同一枚硬币的两面：一个管"该不该多用组件"，一个管"该用哪个组件"。

## 17. Design Critique（设计自评，生成后执行，含强制阈值）

页面生成后（HTML/CSS 产出之后），必须再跑一次 Design Critique，这是独立于 `validation.md` 合规检查的另一套检查——合规检查回答"这个页面有没有用假组件/编数值"，Design Critique 回答"这个页面有没有设计感、产品判断对不对"。检查这些项（2025-08扩容）：

- **A. Visual Focus**：Primary Visual Focus 是否清晰可辨认，是否真的只有一个？
- **B. Information Hierarchy**：Visual Hierarchy 阶段的判断是否在最终产出里真的体现了出来？
- **C. Composition**：Page Composition 阶段选定的 Composition Pattern 组合，是否被完整落地？
- **D. Spatial Rhythm**：是否满足第13-14节的密度分层和节奏交替要求？
- **E. Content Density**：单屏信息密度是否合理？
- **F. Visual Consistency**：页面内部视觉语言是否统一（跟 `validation.md` 的 Token一致性检查不是一回事）？
- **G. Template Detection（模板检测）**：页面是否退化成了 `White Background + Card + List + Divider + Button` 这个固定模式？覆盖页面70%以上内容区域即判定失败。
- **H. CTA 突出度**（新增）：核心 CTA 视觉权重是否明显高于其他可点击元素？
- **I. Tab 合理性**（新增）：如果页面用了 Tab，是否满足第9节 Tab Intelligence 的存在性判断，不是机械加的？
- **J. Tag 语义正确性**（新增）：PROPERTY_TAG（分类信息）和 STATUS_TAG（业务状态）有没有混用？
- **K. 无意义模块检测**（新增）：有没有不服务于任何 Business Goal/User Task 的模块，纯粹为了"页面看起来更丰富"而存在？
- **L. 业务能力保留**（新增，对应第5节红线）：业务能力保留核对表是否完整、有没有静默丢失的功能点？

**任意一项不通过，尤其是 G/L 两项**：标记 `VISUAL_DESIGN_WEAK`，必须回到 Information Architecture（第5节）或 Layout Hypothesis（第11节）重新调整，不是改几个颜色/间距应付。

**⚠️ 强制阈值（2025-08新增，取代之前"VISUAL_DESIGN_WEAK就返工"的纯定性判断）**：按第18节打 Design Quality Score，**低于85分，必须自动进行第二轮优化**，不是"建议返工"，是硬性规则——回到 Information Architecture 或 Layout Hypothesis 重做，重做后重新评分，直到≥85分，或者对每一项不达标都能给出可核实的具体原因（比如某个纯功能性PR2看板，Visual Focus天然不需要PR1级别的强烈程度，这种要在报告里写清楚为什么，不是绕过阈值）。

**PR3 页面、或本次 Autonomy Level 在 L1 及以下时，不需要跑 Design Critique**。

## 18. Design Quality Score（设计质量评分，独立于 validation.md 的合规评分）

`validation.md` 已有的量化评分（Component Reuse / Token Compliance / Mobile UI / Visual Consistency）测的是"合规性"，这里是测"设计质量"的评分，两者**必须都跑，不能互相替代**：

```
Information Hierarchy   20
Visual Focus             20
Composition              20
Spatial Rhythm           15
Content Density          10
Visual Consistency       10
Component Compliance      5
─────────────────────────
合计                    100
```

**权重设计的用意**：前三项加起来占60分，是评分主体，直接对应 Design Critique 的 A/B/C/G/L 项。`Component Compliance` 只占5分——不能让"组件复用"变成设计质量的主要衡量标准，那样会反过来鼓励"为了拉高这一项分数堆组件"，跟第16节的原则冲突。这一项本身是否达标，仍然由 `validation.md` 的归零规则严格把关，不靠这5分权重体现严重性。

**评分方式**：每一项按 Design Critique 对应检查项的通过程度打分，不是主观拍一个数字。`Component Compliance` 具体等于 `validation.md` 的 `Component Reuse Score`（0-100）× 5%。

**≥85分是第17节的强制交付门槛**，不是可选的参考数字。**这条评分同样遵守"不要为了评分而评分"的原则**：目标是发现设计问题，不是让数字好看，更不是靠降低标准凑够85分。
