# 开发历程（CHANGELOG）

记录这个 Skill 是怎么一步步被真实测试和纠正出来的。看这份文件能理解"为什么会有这条规则"，比只看结果更容易判断以后遇到类似情况该怎么处理。

## 1. 起点：Figma 组件库只读分析

对 Figma 文件「倩雯专用BEP-S组件」（单页 Page 1，45个规范画板）做了完整的只读扫描，产出第一版《BEP-S AI UI 组件规范 v1.0》，识别出：

- 全库 45 个规范画板，128个带斜杠层级命名的真实 Instance 引用，53个真变体 Component
- 完整的色彩/字体/间距/圆角/阴影 Token
- 一个关键结构性发现：**这个 Figma 文件本身没有绑定 Variables，且真实主组件全部来自一个已经断开订阅的外部远程库**——文件里能用的"真实组件"，都是靠克隆 Page 1 上已有的历史 Instance 得来的，不能用 `importComponentByKeyAsync` 导入新的。

## 2. 转成 Claude Code Skill

把分析结果转成正式 Skill 结构（SKILL.md + 5个配套 .md 文件），核心原则：组件选用优先级（真实Component > Instance > 组合 > 页面模块 > 新建）、绝不修改源组件库。

## 3. 第一次真实生成测试：踩了几个坑

第一次真拿 Figma MCP 实测生成"信息登记"表单页，过程中发现：

- **相似组件魔改陷阱**：如果目标组件不存在，容易图省事拿一个相似组件改一改冒充——比如把 Input 拉高冒充 Textarea。这条踩坑之后新增了"禁止相似组件魔改"的硬性规则。
- **组件状态不能连坐**：找到 Checkbox 的"选中"态是真实组件，不代表"未选中"态也是——穷举扫描后发现未选中态确实是 `NOT_FOUND`。同理 Primary Button 全库不存在，只有 Secondary Button 是真的。
- **Figma MCP 遇到了 Starter 套餐的调用次数上限**，中途被打断，只能凭已经拿到的数据继续出方案。

这次测试之后，把这些教训写成了 `component-library.md` 的第2a/2b节规则，并且验证了 Token 可信度分级（`FOUND_IN_FIGMA`/`INFERRED`/`NOT_DEFINED`/`AI_PROPOSED`）。

## 4. 架构转向：不依赖 Figma MCP

Figma MCP 是按额度计费的外部服务，额度有限（上一步已经实测触发过上限）。把整个 Skill 的架构从"每次生成都可能查 Figma"改成：

```
Figma → 一次性核实 → 结构化 Registry（JSON） → Claude 独立生成 → 需要时才回查 Figma
```

新增了 `component-registry.json` / `design-tokens.json` / `missing-components.json` / `design-system-conflicts.json` / `page.schema.json` 这几个数据层文件，`.md` 文件降级为"推理层"（解释为什么）。SKILL.md 重写了整个生成流程，默认全程不调用 Figma MCP，只有四种明确情况才考虑调用。

## 5. 真实生成测试（不依赖 Figma）：报修申请

拿"报修申请"表单页完整走了一遍新流程——读 Registry、出 Component Mapping 报告、生成 HTML+CSS、用本地浏览器（不是 Figma）验证渲染效果、自动修正发现的问题（比如 CSS 里几处没有 Token 依据的魔法数字、`safe-area-bottom` 这个 Token 被同一页面用了两次不同语义）。证明了"设计阶段完全脱离 Figma MCP"这条路径是可行的。

## 6. 真实数据修正：表单布局

用户直接给了一张 Figma「表单」组合范式画板的截图，指出真实布局是"标签左、值右"的单行结构，不是之前假设的"标题在上、内容在下"堆叠结构。这次更正教会了一件事：**同一批 Figma 文本数据（比如标题和值字号都是18px）本身就暗示着布局线索，之前没读出来是判断力问题，不是数据不够**。同时发现那张画板本身是 SPEC_ONLY 的示例页，"未选中/已选中"是占位文案，不是真实业务选项——生成页面时不能照抄示例内容。

修正写回了 `component-registry.json`（新增 `layoutPattern` 字段）和 `component-library.md`，标注来源是"用户提供的截图"，跟 `use_figma` 实测验证区分可信度等级。

## 7. 补交互与自适应规范：接入外部标准

用户发现 Skill 里只有静态视觉规范，没有点击交互、状态反馈、动效、自适应这些。因为 BEP-S 的 Figma 源文件本身就没有这类数据（静态设计文件，没走 Prototype 连线），所以引入了 Apple HIG / Material Design 3 / WCAG 这几个外部权威标准来填空白，新增了 `EXTERNAL_STANDARD` 这个可信度等级——专门指"BEP-S没定义，但有具名外部来源"的数据，跟"AI瞎猜"（`AI_PROPOSED`）明确区分开。

## 8. 真实生成测试：任务执行页（复杂业务页）

拿一张真实业务原型截图（催收任务执行页）生成对应设计，这次的重点是**不照抄原型的配色**——原型用的暖黄色不是 BEP-S 验证过的品牌色，全部换成了真实的 `color.brand.3`。这次测试也顺带确认/发现了新的组件缺口（进度条、小尺寸按钮、部分业务图标），并把 Progress Bar 的优先级从 P2 上调到了 P1（因为遇到了真实业务场景）。

## 9. 卡片投影：两次更正

- **第一次**：用户指出"卡片没有投影"，但规范画板其实同时记录了"有投影"和"无投影"两种变体——所以更正为"默认用无投影"，第一版处理方式是改用描边(border)代替投影。
- **第二次**：用户指出"卡片也没有描边"——默认状态是投影和描边都不加，纯靠卡片背景色跟页面背景色的对比区隔。这次顺带在浏览器实测里抓到一个真实 CSS bug：`.method-card` 是个 `<button>`，删掉显式 border 之后，浏览器默认的按钮描边（2px outset）冒了出来，得显式加 `border: none` 才行。

这两次修正告诉我们：**规范画板记录的"多种变体都存在"不等于"AI可以自己选一个默认值"，默认值需要业务方确认，不能靠画板顺序或者视觉习惯猜。**

## 10. 图标库：接入 Ant Design Icons

用户反馈手绘 SVG 图标"太丑了"。没有退而求其次继续手绘或者贴牌造假，而是真的用 `curl` 从 Ant Design Icons（MIT协议）官方仓库拉取了原始 SVG 源文件，新增 `icon-library.json`/`icon-library.md`，图标数据标 `EXTERNAL_STANDARD`，跟之前的 `AI_PROPOSED` 手绘明确区分。选 Ant Design 的原因：MIT协议可商用、企业级线性图标风格跟 BEP-S 的物业管理类调性贴合。

## 11. 真实生成测试：履约任务详情页

按新规则（卡片无投影无描边 + 真实图标库）一次性生成对了，没有再返工。这次发现了新的组件缺口"提示横幅 Alert Banner"（跟 Toast 不是一回事——Toast是浮层轻提示，这个是页面内容流里常驻的一块）。也验证了一处 AI 判断力：正确排除了原型截图右下角一个明显是截图工具浮层、不属于页面设计本身的"演示"胶囊标记。

## 12. 主色覆盖：#006D9B → #00B1B4

用户直接要求把品牌主色换成 `#00B1B4`。这不是对之前读值的更正——`#006D9B` 确实是从色彩规范画板截图真实读到的，读取没有问题，这是团队主动要求的换色。为此新增了第五个可信度等级 `USER_OVERRIDE`：优先级高于一切（包括 `FOUND_IN_FIGMA`），因为用户当下的指令比历史读值更权威；同时原始读值保留在 `originalFigmaValue` 字段里，不会因为覆盖就丢失可追溯性。三个已生成的测试页样式表同步更新并在浏览器里复核过效果。

## 13. 打包交付

把以上所有内容整理成正式交付版本：补充 README.md（人读）、CHANGELOG.md（就是这份）、把三次测试生成的页面收进 `examples/` 目录，整体打包保存，供团队内其他人直接使用。

## 14. 金刚区图标彩色化 + 一处 AI 判断力修正

同事用打包好的 Skill 跑出「履约工作台」页面后反馈"icon 都很粗糙"，先确认"继续用 Ant Design Icons、这次更新图标库+出一版示例页"再动手（因为图标库选型改动影响面大，值得先确认）。过程中发现两个问题：

1. **金刚区太平淡**：扫码核销/订单任务/门店配送/异常处理这4个快捷入口图标虽然是真实开源图标（不是手绘造假），但线性单色风格用在"金刚区"（图标宫格快捷入口）这种天然偏 C 端消费级语言的模块里显得像设置页。新增 `icon-library.json` 的 `colorfulIcons` 分组，源换成 Microsoft Fluent Emoji（Color 风格，MIT License，同样是真实拉取不是手绘），并把这条规则写成正式规则：金刚区用彩色图标+统一中性背景，B端功能图标（导航栏/表单/列表行内）仍用线性单色 Ant Design Icons，两套图标库是场景分工不是新旧替代。规则详见 `icon-library.md`「金刚区专用规则」和 `component-library.md`「5. Grid」的更正说明。
2. **一处不该问的问题**：用户问"为什么异常处理的icon是黑的"时，第一反应是把黑/红两个选项抛给用户选，被用户直接纠正"你要按自己的理解去设计呀"——这类纯视觉判断（不是数据可信度、不是业务规则）应该自己拿主意，问用户反而是没担当。这次顺带确认：把4个图标统一换成彩色 emoji + 统一中性背景之后，黑/红的矛盾自然消失了（不再有任何图标用强调色背景），不需要在两个不理想选项里选一个。

同时在这次浏览器实测里，顺带验证了前一轮发现的 `.bottom-tabbar` 高度/安全区 padding 冲突 bug（见「页面尺寸/安全区域」章节）已经用 `min-height` 方案修复生效，图标不再被压缩成 0 高度。

**这次的教训**：图标库选型这种影响多个已生成页面的改动，值得先跟用户确认方向；但同一批改动里遇到的纯视觉细节判断（这个图标该用什么颜色），不需要每次都抛回给用户，AI 应该自己判断并说明理由，这是两类不同性质的决策，不能用同一个"是否要问用户"的标准处理。

## 15. 金刚区彩色图标：查了四个候选都不理想，新增 PLACEHOLDER 状态；B端单色图标换源到字节 IconPark

用户看了第14节的彩色图标（Fluent Emoji Color风格）后，发来一张真实App（哈啰出行）金刚区截图，指出风格不对，要求"先和我确认再开始工作"——这是一条关于"图标库选型要先确认"的复用指令（跟第10节接入图标库时的确认要求同一逻辑），所以没有直接动手换库，先做了research：

**排查过程**（详细记录见 icon-library.md「金刚区专用规则」）：
- Fluent Emoji「3D」风格（同库另一种渲染）：比Color风格更接近参考截图，但用户看了实物截图仍反馈不理想。
- 字节 IconPark：查证后只有纯色/双色/四色平铺主题，没有渐变玻璃质感，风格不匹配。
- 3dicons.co：CC0协议免署名，风格（玻璃质感+高光+阴影）是几个候选里最接近参考截图的，但查了完整目录（约200个图标）**没有**扫码/卡车配送/订单清单/警告这几个具体图标。
- Icons8 3D系列：大概率风格和覆盖度都够，但免费版要求署名（挂icons8.com链接），付费才能去掉，这个决定不该AI替业务方做。

四个候选都有明显取舍，用户最终决定："让设计团队出定制图标，先用占位图撑版式"。这个结论倒逼新增了一个可信度状态：`PLACEHOLDER_PENDING_DESIGN`（写入 `design-tokens.json` 的 `usageRule`）——跟 `AI_PROPOSED`（"没有更好来源，AI给的建议值/近似图形，可长期使用"）不是一回事，`PLACEHOLDER_PENDING_DESIGN` 是"明确知道这不是最终方案，只是临时占位，报告里必须说明后续要被设计团队的定制资产替换"。金刚区图标继续复用之前拉取的 Fluent Emoji Color 素材（视觉上比留白/纯色块更有辨识度，方便评审版式），但 `data-bep-status` 从 `EXTERNAL_STANDARD` 改标 `PLACEHOLDER_PENDING_DESIGN`，不能再让人误以为这是定稿方案。

**同一轮里用户还确认了一条独立的决定**：B端功能性单色图标（导航栏/表单/列表等，非金刚区）把库从 Ant Design Icons 换成字节跳动 IconPark——这条跟金刚区彩色图标的取舍无关，是纯粹的选型偏好，两个库客观上都合规靠谱。换源过程中发现 IconPark 的图标源文件是 JS 字符串拼接（不是现成 SVG 文件），第一版解析脚本因为正则没处理好 `' + props.xxx + '` 这种拼接语法，生成的 SVG 全是空属性（宽高、颜色都是空字符串），图标完全不显示——用浏览器截图对比预览时才发现问题，说明"脚本跑通不报错"不等于"产出内容是对的"，这类第三方源码解析类工作必须实际渲染出来看一眼，不能只看脚本退出码。修好解析逻辑后，还用 IconPark 官方 `runtime/index.tsx` 里的 `DEFAULT_ICON_CONFIGS` 常量核实了 outline 主题的官方默认渲染参数（颜色/描边粗细/端点样式），不是凭感觉指定的数值。换源时顺带把几个语义不够准的图标换成了更贴切的同义项（"门店配送"从泛用的 `Car` 换成图形更清晰的 `Truck`，"工作台"从形状不搭的 `AppStore` 换成网格图标 `AllApplication`，两者都是先批量截图预览对比过才定的，不是凭图标名字猜的）。

**这次的教训**：查证一个"这个库有没有某个具体功能特征"的问题（比如"有没有渐变质感"），光看文档描述不够，需要真的去看目录/截图核实，几次搜索都是从"听起来应该有"到"查了发现没有"；解析第三方源码格式产出可视化资产时，必须实际渲染验证，不能假设脚本没报错就是对的。

## 16. 金刚区图标第三次更正：换成 Solar Icons（Bold Duotone），接受CC BY署名

第15节的占位方案（Fluent Emoji Color 撑版式，等设计团队出定制资产）只是过渡。用户又发来一张不同风格的参考截图（车服类App金刚区：剪影主图形+同色浅透明度高光角标，比之前"哈啰"那张玻璃质感3D风格更扁平），问"这种风格能找到吗"。这次查证过程顺利很多——通过 [Iconify](https://iconify.design)（一个聚合多个开源图标集、提供统一API的平台）查到了 **Solar Icons**（作者480 Design，7476个图标，`Bold Duotone`主题正好是"单色+opacity=.5背景层"的双色层次结构，跟参考截图的视觉逻辑一致），而且四个具体图标（`qr-code`/`clipboard-list`/`delivery`/`danger-triangle`）都有现成、贴切的对应项——`delivery`这个图标名字都跟"门店配送"字面对应，比之前任何候选的语义匹配度都高。

唯一的问题是协议：Solar 用的是 **CC BY 4.0**，需要署名，不是之前用惯的那几个免署名协议（MIT/CC0）。这次没有自己拍板"署名可以接受"，而是把取舍摆清楚（风格匹配度高 + 协议要求署名 vs 之前免署名候选风格不匹配/覆盖不全）问用户，用户确认"接受Solar署名，用它"。落地时没有只在Registry文档里写一句"需要署名"就算了事，而是真的在生成的示例页面里加了一行可点击的署名（页面最底部"部分图标来自 Solar Icons by 480 Design（CC BY 4.0）"），把这当成一个必须在页面里体现的真实合规要求，而不是纯文档提醒——因为署名要求是"即使 AI 不在场，工程团队直接抄这份 Registry 生成页面也不会漏掉"的东西，光靠 Registry 里一行文字提示是不够的，最好的方式是在生成流程里就把它当成页面的一部分产出。

同时确认了一件事：这套图标允许"按语义分别配色"（扫码/配送用蓝色，订单用橙色，异常用红橙色），不用像B端单色图标那样强制全部同色——因为 Bold Duotone 这个设计语言本身就是靠色相区分功能，跟线性单色图标的"颜色统一交给外层容器控制"是两种不同的设计逻辑，写进了 icon-library.md 的规则里，不是随手配的颜色。

**这次的教训**：署名类的合规要求，写进内部文档不等于会被真正执行——尤其是这个 Registry 未来可能被其他人（甚至不是通过对话，而是直接读文件）拿去生成页面，最可靠的做法是让署名本身成为生成产物的一部分（页面里的一行文字），而不是纯靠"文档里写了应该有人记得"。

## 17. 署名落地方式被否决重做：不该塞进业务页面

第16节里为了让署名"真的被执行"，把 CC BY 4.0 的署名直接做成了业务页面（履约工作台）底部一行可见文字。用户反馈"这样肯定不行"——确实不实用，正常产品不会在每个业务页面挂第三方素材署名，这不是行业惯例，真去用会显得很奇怪。

改正为：署名应该集中放在 App 统一的一处（"设置-关于-开源软件声明"类页面），业务页面本身不需要携带任何可见文字。这是 App 级别的一次性工程配置，AI 生成页面时的责任是在报告里提醒"这个App需要有开源软件声明页收录这条署名"，不是把文字塞进每个生成的HTML里。移除了demo页里的署名文字，改成HTML注释标注"这里欠了一处署名，见icon-library.md"，`icon-library.json`/`icon-library.md`/`SKILL.md` 三处都同步改了说法。

**这次的教训**：第16节"让署名成为生成产物的一部分"这个思路本身没错（合规要求光写文档确实容易被忘），但"生成产物"想窄了——以为只能是"页面里的一行文字"，其实"报告里的一句提醒"也是生成产物的一部分，而且更符合真实产品的落地方式。解决"容易被忘"的问题，不等于必须用"塞进UI"这种最直接但也最粗暴的方式。

## 18. 图标颜色踩坑：`icon.color` 复用 `color.text.*` 被理解得太死板

用户发来两张同事用 skill 跑出来的新页面截图（「开始配送」「配送异常处理」），指出红框标出的图标都是黑色背景/黑色。逐个诊断：

- 「配送异常处理」页红色警示条里的感叹号图标，被渲染成了 `color.text.5`（黑色），但警示条本身用的是 `color.danger.1`背景+`color.danger.7`红字——图标颜色跟周围语境完全对不上，是真实的规则理解漏洞：`icon.color` 复用 `color.text.*` 这条 `FOUND_IN_FIGMA` 规则的本意是"图标跟随所在语境的文字颜色"，之前理解得太字面，遇到没有更具体指示的图标就无脑套用最深的 `color.text.5` 兜底，没有意识到应该先看图标所在容器有没有已经确定的语义色（danger/warning/brand），有就跟着语义色走。
- 「开始配送」页缩略图上的删除 X 按钮是黑色圆角按钮，这个不一定是错的——深色/半透明按钮盖在图片缩略图上是常见惯例（要在任意图片内容上都有对比度），如果这块走的是 BEP-S 真实 Upload 组件 `INSTANCE`，黑色本身就是 Figma 里的真实设计。因为看不到这两个页面实际生成时走的是真实 Instance 还是 Registry 兜底，如实告诉了用户这条不能替他们确认，请他们发源码来核实。

这次没有把两个现象混为一谈一起"改成别的颜色"，而是拆开诊断——一个是真实规则漏洞，一个可能是合理的既有设计，草率地把两个都改掉反而会破坏可能本来就对的东西。规则修正写进了 `design-tokens.md`/`design-tokens.json` 的 `icon.color` 条目和 `validation.md` 的检查清单：图标颜色要先判断所在容器/文字有没有语义色，有就跟着走，没有才退回 `color.text.*` 按视觉权重选级别，不能统一套用 `color.text.5`。

**这次的教训**：`icon.color` 复用 `color.text.*` 这条 Token 之前在 SKILL.md/design-tokens.md 里都只写了"是什么"（复用哪个Token），没写"怎么用"（复用的是哪一级、跟局部语境的关系）——这类"看起来定义清楚了，实际执行时有二义性"的 Token，光记录数值本身不够，还要记录清楚它在不同场景下具体怎么取值，不然会在不同页面反复踩同一个坑却看起来像是"每次都是新问题"。

## 19. 必填星号排列顺序更正：标题在前，星号在后

用户发来「开始配送」页截图，指出"*配送员"这种星号在标题前的写法不对，星号应该排在标题文字**后面**（"配送员*"）。查了 Registry：`component-registry.json` 的"必填星号"条目此前只验证过这个嵌套子组件（`数据录入/标题/带星`）"能不能切换显隐"，从来没单独验证/记录过它在标题内排在文字前面还是后面——之前生成时凭直觉套用了通用网页表单惯例（星号在标题前），没意识到这跟 BEP-S 实际规范是反的。

**这次的教训**：一个真实组件"能做什么"（比如切换显隐）被验证过，不代表它"具体长什么样"的所有细节都验证过了——组件内部子元素的排列顺序这种容易被想当然套用通用惯例的细节，即使组件本身是真实 `INSTANCE`，也可能因为没有单独截图核实布局而被想当然地做错，这跟之前"Input/选择触发行 到底是堆叠还是同行"是同一类坑（component-library.md 第6节），都是"结构真实存在，但具体呈现方式没读对"。

## 21. 选择触发行箭头太细：IconPark 默认粗细跟真实组件对不上

用户发来「选择触发行」真实组件的截图，指出右箭头比生成页面里的粗很多。之前用 IconPark 的 `Right` 图标时，直接套用了它 outline 主题的官方默认 `stroke-width=4`（这个默认值本身有据可查，不是瞎猜），但没有意识到"官方默认值"不等于"适合这个具体场景的值"——在小尺寸（20px）展示时，`stroke-width=4`（相对48的viewBox）显得偏细，跟真实组件截图里明显更粗的箭头对不上。

## 22. 一级/二级 Tab 摆放顺序规则补全

用户发来两张截图：一张是同事生成的订单列表页（顶部是"全部订单/实物商品/数字商品"胶囊 Tab，下方是"待处理/处理中/已处理/全部"下划线 Tab），另一张是组件库规范画板里"一级Tab/二级Tab"的真实样式示例（一级=下划线在上，二级=胶囊在下）。两相对比，同事生成的页面把顺序摆反了——胶囊(二级样式)在上，下划线(一级样式)在下。

`component-library.md`「标签栏 Tab」这一节之前只记录了两级 Tab 各自的字号(18px/16px)和样式(下划线/胶囊)，没有记录"两级同时出现时谁在上谁在下"这条摆放规则——这是个真实的规则空白，不是执行时漏看了已有规则。这次直接补全，用"管辖范围大小"作判断依据（范围更大更总的类别用一级下划线摆上面，依附于当前一级选择结果的细分状态用二级胶囊摆下面），而不是"哪个视觉上更显眼就放上面"这种容易主观判断错的标准。

**这次的教训**：一个组件规范只记录"长什么样"是不够的，涉及组件组合使用时"怎么摆放/谁在前谁在后"这类结构性规则同样需要显式记录，不然生成时容易凭直觉排布，尤其是像这次这样两个层级本身样式差异不大（都是Tab），仅从字面"一级/二级"很难猜对哪个该在视觉上更靠前。

## 23. 标签拆分为"普通标签"和"状态角标"两个组件

用户发来两张截图：一张是同事生成的订单卡片列表，红框标出"到店自提"和"待自提"两个标签视觉上做成了一样的内联胶囊；另一张是规范画板里"状态角标"的真实样式——悬挂在卡片右上角、右上角圆角贴合卡片圆角的一种特殊标签，跟内联小色块完全是两个东西。

`component-registry.json`/`component-library.md` 之前只有一个笼统的"标签 Tag"条目，`usage` 字段写的是"内容分类/状态标记"，把两种不同性质的信息（固定属性 vs 业务状态）混在一个组件定义里——这是规则本身的疏漏，不是执行时没照做。这次拆成两个独立条目：**标签（普通）**同行内联，回答"这是什么"；**标签（状态角标）**卡片右上角悬挂、右上角圆角贴合卡片圆角，回答"现在是什么状态"。判断口诀是"会不会随业务流程变化"——不变的用普通标签，会变的用状态角标。

**这次的教训**：跟第22节一级/二级 Tab 的教训是同一类问题——一个组件条目的 `usage` 字段如果同时描述了两种不同性质的使用场景（这次是"分类"和"状态"两个词一起出现在一条规则里），很可能是该拆成两个组件却被偷懒合并了。以后写组件规则时，`usage` 里如果出现"或"字连接两种明显不同的语义，要停下来想一想这是不是该拆分的信号。

## 24. 一级Tab样式二次更正：平分布局 + 独立指示条精确尺寸

「订单列表」demo 生成后，用户反馈"tab样式之前是对的，为什么改错了"。先确认了一件事——第22节"一级/二级Tab摆放顺序"这条规则本身没错，一级(下划线,全部订单/实物商品/数字商品)在上、二级(胶囊,待处理/处理中/已处理/全部)在下，这个内容-层级对应关系用户确认是对的。问题出在一级Tab的**具体样式实现**上，用户直接给了三个精确数值：三个入口要平分整行宽度（不是左对齐+固定gap），选中指示条是24px宽×2px高、全圆角的独立小色块（不是给文字元素加border-bottom，那样宽度会跟着文字长短变、且是直角）。

这次没有靠自己猜测复原，是通过 AskUserQuestion 先确认了"到底是内容层级映射错了，还是具体样式细节错了"——一开始设想了两种可能（内容对应关系反了 / 样式细节不对），用户选择了后者并给出精确数值，避免了在错误的方向上继续返工。改用 CSS `::after` 伪元素实现指示条，脱离文字容器的 border，独立控制尺寸，`justify-content:space-between` 替换原来的 `gap:24px` 布局。浏览器实测过 `getComputedStyle` 精确匹配 24px/2px/9999px 三个数值。

规则更新写回了 `component-registry.json`（页内标签栏条目新增精确尺寸字段）和 `component-library.md`（一级Tab样式二次更正说明）。

**这次的教训**：用户说"之前是对的、现在错了"这种反馈本身信息量不够——"之前"可能指内容层级关系，也可能指具体某个样式细节，两种理解会导向完全不同的修改方向。遇到这种模糊反馈，与其凭第一反应直接动手改（容易改错方向、浪费一轮），不如先用选择题式的问题把"错在哪个维度"锁定下来，尤其是当我自己也无法重新看到原始参考图、只能靠记忆和推理时，主动补一步确认比自信地猜一个方向更省时间。

## 25. 图标粗细问题不是孤立个案，全库统一调粗

「订单列表」demo 修好 Tab 样式后，用户又反馈导航栏返回箭头、搜索图标、筛选图标"又变粗糙了"。先实测了这几个图标当前的有效描边像素（`getBoundingClientRect` + `stroke-width` 换算）：返回箭头2px、筛选2px，搜索图标只有1.5px——印证了确实偏细。这跟第21节"选择触发行箭头太细"是同一个根因（IconPark outline主题默认`stroke-width=4`，在BEP-S常用的18-24px小尺寸场景下都显得单薄），但第21节当时判断"没证据的地方不跟着一起动"，只单独给选择触发行开了个 `chevron-right-bold` 变体。这次同样问题在另外三个不相关的图标上重复出现，说明证据已经从"个别案例"升级成"系统性规律"，于是把判断升级：把 `icon-library.json` 全部16个IconPark图标的 `stroke-width` 统一从4改成6，`chevron-right-bold` 也合并回了主条目（不再需要区分粗细两个版本），同步改了三个受影响的demo页面（订单列表/履约工作台/审批单填写），浏览器逐个重新截图确认，无console报错。

## 26. 新增独立的一层：C端视觉设计层（不是继续优化组件识别）

用户明确叫停了"组件识别"这条主线的持续优化——"BEP-S 组件库已经识别成功，Component Registry、Design Token、组件状态等基础能力已经完成"，转而指出一个此前 Skill 完全没覆盖的新维度：**组件和Token都用对、移动端规范也满足，但页面视觉结果普遍缺乏设计感**——大量纯白背景、结构过度模板化、一二级页面视觉层级没区别、首页缺少焦点、运营页缺少氛围和节奏、页面像"组件拼装"不像成熟C端App、AI过度追求组件复用率反而牺牲了构图、所有页面都是"NavBar+白底+Card+List"固定模板。用户明确要求"不要通过增加更多组件来解决"，要在不破坏现有组件库/Token/规范的前提下新增一套独立的「C端视觉设计层/页面构成规则」。

这是一次**架构级新增**，不是修正某条已有规则：

- 新增 [c-end-visual-design.md](c-end-visual-design.md)，核心是"页面分级"（T0首页/T1运营活动页/T2内容推荐页/T3二级功能页），先判断页面属于哪一级，再决定要不要往下看背景策略/首页焦点/活动页节奏这些规则——T3（列表/表单/详情/设置）维持组件化规整结构就是正确答案，不需要额外加视觉修饰，问题只出在把 T0/T1/T2 也做成了 T3 的样子。
- 新增背景策略（不引入库外新颜色，只用已有Token做色块分区/渐变/满版图片+穿透卡片）、首页焦点模块规则（体量明显大于普通列表卡片）、活动页节奏编排规则（密度/背景/图文比例要交替，不能均质）、"组件拼装感"自诊断清单。
- 补了一条此前缺失的核心原则："组件复用率是元素级指标，不是页面级指标"——单个按钮/输入框依然要优先复用真实组件，但页面整体的模块大小/间距/背景/焦点不受复用率约束，不能为了拉高复用率数字牺牲构图。这条写进了 `SKILL.md`「核心原则」。
- `SKILL.md` 生成流程里插入了 Step 2.5（页面视觉分级判断），`page-patterns.md` 顶部和 Home Page 模板都加了指向这份新文件的提醒，`validation.md` 顶部说明"合规检查"和"设计感检查"是两件分开的事。

**这一层的诚实性框架**：这份文件的内容不是从 Figma 读出来的（BEP-S 源文件本身没有页面级构图/氛围数据），明确标注为 AI 建立的设计判断层，使用时标 `AI_DESIGN_DECISION`（不是 `AI_PROPOSED`——后者用于组件缺失时的替代方案，这里没有组件缺失，是主动的构图判断，性质不同），且不改变、不覆盖任何现有红线（真实组件优先、Token优先、禁止发明组件、禁止改真实组件、移动端规范、组件缺失如实标记全部保留）。

**这次的教训/记录意义**：这是 Skill 第一次从"数据准确性"（组件是否真实、Token是否正确）扩展到"设计判断力"（页面构图是否成熟）这个新维度，两者需要的能力和验证方式完全不同——前者靠查证 Figma 数据，后者靠设计判断力+用户反馈迭代，不能用同一套"如实标注可信度"的框架就假装解决了"好不好看"的问题，所以特意在文件开头写清楚这一层的性质，避免以后跟其他数据层混淆。

## 27. AI UI Design Reasoning Layer：从"规则清单"升级为"推理流程"

## 28. AI Design Brain：从"设计推理流程"升级为"产品+设计双重判断权"

第27节的 `visual-design-reasoning.md` 解决了"页面构图该怎么想"（Business Goal→Visual Hierarchy→Layout Hypothesis→Page Composition），但在两次真实原型截图测试（"履约值守台"、"履约工作台"，均要求"只把这张图当成原型需求，先做UE设计……不要参考他的设计，独立按照设计师的思路去设计"）后，用户发现第一次的信息架构改版**只是把原型里的模块视觉重排了一遍，分类轴本身照抄了原型**——用户直接指出："好像信息架构并没有做设计，请根据页面的功能，重新进行信息架构设计"。这次批评之后，用户给出了更大的诊断："Skill 更像「组件拼装器」，而不是「产品设计师」——AI 会"使用组件"，但不会"设计页面""，要求把 Skill 升级为「Product + UX/UE + UI + BEP-S Design System」，明确列出8项要新增的能力：Product Thinking、Information Architecture（AI 有权重组，但不能删业务能力）、UX/UE Thinking（任务路径/首屏/交互/状态设计/高低频）、Visual Design Thinking、Component Intelligence（先判断语义意图再选组件）、Design Autonomy（L0严格还原→L4产品级自主设计，5级）、Tab Intelligence（判断该不该存在Tab）、AI Design Critique（85分强制阈值）。用户同时划了一条不可动摇的边界："原型不是最终设计，原型只代表业务需求和功能集合——AI 必须拥有设计判断权，但不能无理由改变业务目标和删除业务能力"。跟之前几轮一样，用户要求先只出架构方案、不动文件，方案确认后才落地。

**命名冲突处理**：新的 Design Autonomy 用户直接指定用 `L0-L4` 表示，但 `L1/L2/L3` 这三个字母组合已经被第27节的 Page Role 占用了。落地前主动识别出这个冲突并提出解法：把 Page Role 改名为 **PR1/PR2/PR3**（Page Role 的缩写，跟旧 T0-T3 的历史映射关系不变），把 `L0-L4` 留给 Design Autonomy Level——这样两个维度（"这是什么类型的页面" vs "AI这次能在这页面上改多少"）在名字上就不会互相冲突，含义也更直白（PR 一眼就是 Page Role，不用记"L1是首页那个"）。

**没有新建大量文件，选择了整合进现有结构**：延续第27节"清单式思维本身就是问题"的教训，这次同样没有为8项新能力各开一个新文件，而是把 Product Thinking / Information Architecture / Design Autonomy Level / UX-UE Thinking / Tab Intelligence 都并入 `visual-design-reasoning.md`（升级为"AI Design Brain"，从原来的12项能力扩到19节、13阶段Pipeline），只在 `component-library.md` 新增一个 0.5 节（Component Intelligence）、在 `page-patterns.md` 新增一个 Composition Pattern（Empty State Block）、在 `validation.md` 扩展 Design Critique 检查项（A-G 扩到 A-L）——保持"一个入口文件负责讲清楚为什么、周边文件只放执行细则"的既有结构，没有增加新的顶层文件。

**这一轮新增的核心内容**：
- **Design Autonomy Level（L0-L4）**：按 Page Role 给默认值（PR1默认L3-L4/PR2默认L1-L2/PR3默认L0-L1），用户说"严格按原型"强制拉回L0，用户也可以主动要求调高。这是这轮新增里唯一一个"AI可以改多少"的量化刻度，之前的版本只有"该不该做设计"的二元判断（L1/L2必经Step3.5，L3跳过），没有"做到什么深度"这个中间维度。
- **Product Thinking 第④步——功能优先级判断**：原型里每个功能点标"前置/保持/弱化/合并"并写明理由，这份清单是后面信息架构重组的唯一权威依据，不能跳过、不能等到画到那个模块时才临时决定。
- **业务能力保留核对表**：这是这一轮里最重要的红线，直接对应用户"不能无理由改变业务目标和删除业务能力"这条要求——不管 Design Autonomy Level 多高，AI 重组信息架构后都必须逐条核对原型的每个功能点在新方案里能不能找到对应位置，找不到必须停下来跟用户确认，不能自己决定删除，这条不因 Autonomy Level 降低而免除。这条规则直接解决了本节开头"信息架构没做设计"那次批评背后更深的风险——真正的重新分类意味着原型的模块名字、位置都可能整体消失不见，如果没有一张核对表兜底，AI 的"设计判断权"很容易滑向"悄悄丢功能"。
- **UX/UE Thinking**：任务路径、首屏策略、高低频功能差异化、每个数据模块的空/错/加载态怎么处理（复用真实 Empty 组件，不是手绘占位图）。
- **Tab Intelligence**：先判断"这里到底该不该有 Tab"（要有≥2个互斥且用户会主动筛选的分类维度，且每类都有足够内容），通过了才进 `component-library.md` 查具体样式——防止"看着像列表就顺手加个Tab显得规整"这种误用。
- **Component Intelligence**：把 `component-library.md` 里已有的 Tag（PROPERTY_TAG普通标签 vs STATUS_TAG状态角标，见第23节）判断方法推广成一套通用方法论——先判断这段内容的语义意图，再决定组件方向，覆盖 Button(主要CTA) vs 文字按钮(次要)、Card(独立单元) vs Cell(列表行)、Radio(互斥) vs Checkbox(多选)。
- **Design Critique 从 A-G 扩到 A-L**：新增 H(CTA突出度)/I(Tab合理性)/J(Tag语义正确性)/K(无意义模块检测)/L(业务能力保留)。**Design Quality Score 85分变成强制阈值**——低于85分必须回到 Step 3.5 重新调整构图，不再是"建议"，跟原来"不通过就回去改"的措辞相比，这次明确了一个数字线，避免"改了一点点颜色就当作过了"这种敷衍式返工。

**这次的教训**：跟第26/27节一样，问题不是靠"再加一条规则"能解决的，而是每次用户指出的缺口都比上一次更往流程上游走——第26节是"页面构图没设计感"（视觉层面），第27节是"选组件前没有设计过程"（流程层面），这次是"信息架构本身还是抄的、功能取舍从来没有独立判断过"（产品层面，比设计更上游）。这提示了一个规律：以后如果生成结果又被指出"看起来是XX，但其实还是没有真正判断"，大概率不是这一层规则不够细，而是判断链条上还有更上游的一环被跳过了，应该往"根据什么做的这个判断"回溯，而不是继续在当前这一层加检查项。另外，"业务能力保留核对表"这类硬红线的价值在于它是可核对、可失败的（每条功能点要么有对应位置要么没有），跟"多想想视觉效果"这种软性要求不同——以后新增 AI 判断权限时，凡是有"删除/丢失原有信息"风险的地方，都应该配一张类似的核对清单，而不是只靠一句"不能随便删"的原则性提醒。

## 32. 2026-11-03 补上 PRD 入口：从"能不能画"到"拿到需求就能出稿"

**触发原因**：用户提出真实使用场景——"产品给我 PRD 需求，你能直接产出可点击的设计稿"。上一节刚补完可点击原型的**输出**规范，但**输入**这一端是空的：流程从 Step 1"理解需求"开始，默认需求已经是清楚的；而真实 PRD 是业务语言，写着"支持导出报表""支持多级审批""参照 XX 页面"，没有屏幕边界、没有状态、没有字段。直接开画的结果必然是"功能都做了、流程走不通"。

**新增 `prd-to-prototype.md`**（10 节），核心是四件产出物：

1. **需求卡八项**：业务目标 / 角色权限 / 屏幕清单 / 主流程 / 每屏内容块 / 数据字段 / 状态与边界 / 不在本期。填不出来标 `ASSUMPTION`，不许留空。
2. **功能点→屏幕的映射规则**：判据是"**一个用户目标 = 一屏**"，不是"一个功能点 = 一屏"。给 5 条拆屏判据（目标不同/进入路径不同/权限不同/单屏模块>5/返回目标不同）和 3 条合并判据（补充信息/必然同时出现/单独成屏没内容）。
3. **3 问 + 四列假设清单**：只问"不问就整屏会画错"的（角色权限、状态集合、是否必须对齐老系统），最多 3 个；其余写假设，四列是「假设 / 依据 / 影响范围 / 要改改哪里」——最后一列让产品能自己判断改动成本。
4. **PRD 覆盖率核对表**（强制）：PRD 每个功能点一行、原文引用、落点到"屏 + 模块"。覆盖率 <100% 不许交付，除非每处缺口都写了"本期不做 + 谁确认的"。

红线写死一条：**PRD 功能点一个都不能删**。AI 有信息架构和视觉设计的判断权，没有删功能的权力；觉得该砍只能标"建议弱化/合并 + 理由"，交产品拍板。

**流程改动**：SKILL.md 新增 **Step 0**（PRD→需求卡），首次把流程起点从"理解需求"前移到"需求转译"；Step 7C 的多屏原型分支 + Step 6 报告追加三块（需求卡/屏幕清单/覆盖率表）。新增约束 C-90…C-96，其中 C-90/C-92/C-93 是 P0（需求卡完整、功能不删、覆盖率必出）。

**留下的教训**：前两节都在解决"怎么画"，这一节解决"画什么"。一个设计 skill 如果只对**已经想清楚的需求**有效，那它对产品经理的价值就有限——产品经理递过来的恰恰是**还没想清楚的需求**。把需求转译显式写成一步，比在生成时"猜得准一点"可靠得多。
